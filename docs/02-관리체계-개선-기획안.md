# 개인정보처리방침 관리체계 개선 기획안

- 작성일: 2026-08-12
- 소관: 정보보호부
- 선행 문서: `docs/01-benchmark-3사-구조비교.md` (토스증권·카카오페이증권·당사 구조 비교 분석)

---

## 1. 추진 배경 및 목표

### 1-1. 한 줄 정의

> **개인정보처리방침을 "문서(Document)"가 아니라 "구조화된 데이터(Content)"로 관리하고,
> 대고객 홈페이지와 분리된 독립 관리체계를 구축한다.**

### 1-2. 배경

선행 분석(3사 벤치마킹) 결과, 당사 개인정보처리방침은 다음 상태입니다.

| 관점 | 진단 |
|---|---|
| **콘텐츠 품질** | **양호** — 라벨링 20종, 제정일/시행일/최근개정일 3단 구분, 이전본 적용기간 명시. **3사 중 가장 정교** |
| **관리 방식** | **취약** — 위 체계를 전부 수작업으로 유지. 개정 시 개발·빌드·배포 필요 |
| **게시 구조** | **취약** — 화면 ID + 탭 번호로만 식별. 버전이 URL에 없음. 도메인별 사본 존재 |

즉 **이 과제는 부실한 문서를 고치는 일이 아니라, 이미 잘 정의된 체계를 시스템화하는 일**입니다.

### 1-3. 문제의 정량적 근거

| | 토스증권 | 카카오페이증권 | **우리투자증권** |
|---|---|---|---|
| 연평균 개정 횟수 | 5.7회 | 2.2회 | **0.7회** |
| 2026년 개정 횟수 | **10회** | 1회 | **1회** |
| 최근 개정일 | 2026-08-11 | 2026-05-29 | 2026-03-12 |

토스증권은 2026-05-11 / 05-13 / 05-20 / 05-21, **열흘 사이 네 번** 개정했습니다.
정기 개정으로 설명되지 않는 빈도이며, 오탈자·문구·링크 수준을 **발견 즉시 반영**한다는 의미입니다.

반면 당사는 개정 리드타임이 길어 소규모 수정이 누적·지연됩니다. 실제로 현행 방침에는 다음이 남아 있습니다.

- 제12조: "**당행** 앱 이용자의 행태정보 분석을 위해" — 증권사 방침에 은행 표현
- 제6조: "납치, **감긍** 등 범죄" — 오타
- 제15조: 경찰청 사이버안전국 구 URL 사용 가능성 (`cyberbureau.police.go.kr`)

이는 담당자 역량 문제가 아니라 **구조 문제**입니다. 문구 하나 고치는 데 개발 배포가 필요하면,
그런 수정은 "다음 정기 개정 때 함께"로 밀리고 그대로 수년이 지납니다.

### 1-4. 목표

| # | 목표 | 측정 지표 |
|---|---|---|
| 1 | 개정 리드타임 단축 | 문구 수정 기준 **수일 → 당일** |
| 2 | 대고객 게시 정본 일원화 | 게시 위치 **N개소 → 1개소 참조** |
| 3 | 개정 이력 증빙체계 확보 | 버전별 **영구 URL + 스냅샷 해시** 보유율 100% |
| 4 | 홈페이지 재구축 영향도 제거 | 방침 관리 시스템의 **홈페이지 의존도 0** |
| 5 | 조직 변경의 개정 유발 제거 | 인사이동 시 **개정 절차 0회** |
| 6 | **변경내역 자동화 및 대고객 공개** | 신구비교표 **수기 작성 0건** / 버전별 변경내역 공개율 100% |
| 7 | **정책 문서 간 정합성 확보** | 문서 간 중복 기재 항목(조직 정보·위탁현황) **단일 출처화 100%** |
| 8 | **참조 현황의 시점별 입증 확보** | 위·수탁 현황 **버전 보유율 100%** / 임의 시점 현황 조회 가능 |
| 9 | **참조 현황의 고정 주소 확보** | 팝업 → **독립 페이지 전환**. 현황 버전별 영구 URL 보유율 100% |

## 2. As-Is 현황 진단

### 2-1. 현행 업무 흐름

```
정보보호부                         홈페이지 담당부서        개발
   │                                    │                  │
Word/Excel 수정 ──▶ 검토 ──▶ PDF 변환 ──▶ 반영 요청 ──▶ 소스 수정 ──▶ 빌드 ──▶ 배포 ──▶ 확인
                              │
                          이전본 PDF 별도 보관
```

### 2-2. 구조적 문제 9가지

| # | 문제 | 영향 |
|---|---|---|
| 1 | **정본이 복수로 존재** (도메인별 사본 + PDF + 내부 Word) | 개정 시 일부 누락 → 서로 다른 방침이 동시 게시 |
| 2 | **버전이 데이터가 아니라 파일로 관리** (`privacy2.do`, `privacy3.do`) | 특정 시점 방침 특정 곤란 → 분쟁·감독 대응 시 입증 비용 |
| 3 | **과거본에 영구 링크 없음** | 인용·비교·검색 불가 |
| 4 | **콘텐츠 수정이 개발 배포에 종속** | 리드타임 + 법정 시행일 준수 리스크 |
| 5 | **조항 단위 관리 불가** | 제7조만 바뀌어도 전체 재생성. 변경 사유가 데이터로 남지 않음 |
| 6 | **조직 정보가 본문에 하드코딩** | 인사이동마다 개정 절차 전체 재수행 |
| 7 | **변경내역(신구비교표)을 수기로 작성** | 누락이 구조적으로 가능하고 검증 수단 없음. 정보주체가 변경 내용을 직관적으로 확인 곤란 |
| 8 | **위·수탁 현황에 버전·기준일이 없음** | 수탁사가 언제 추가·삭제되었는지 기록이 없어, **특정 시점의 위탁 현황을 입증할 수 없음** |
| 9 | **위·수탁 현황이 레이어 팝업으로 게시됨** | 고유 주소가 없어 **인용·버전 지목·북마크·검색·인쇄가 모두 불가**. 홈페이지 스크립트에 종속되어 재구축 시 경로 소멸 위험 |

### 2-3. 조직 정보 하드코딩 실태 (문제 6 상세)

현행 방침에 다음 정보가 **본문에 직접 기재**되어 있습니다.

| 위치 | 내용 | 변경 빈도 |
|---|---|---|
| 제14조 | CPO 직위·성명 (상무 황돈구) | 인사이동 시 |
| 제14조 | 개인정보 보호업무 부서 (정보보호부) | 조직개편 시 |
| 제14조 | 고충처리 부서 (금융소비자보호부) | 조직개편 시 |
| 제16조 | CCTV 관리책임자 (HR지원부장) | 조직개편 시 |
| 제16조 | **접근권한자 2인의 실명 + 직통번호** | **인사이동 시 (가장 빈번)** |
| 제16조 | CCTV 설치 대수(65대), 설치 지점 | 점포 신설·폐쇄 시 |

→ 이들은 **방침의 내용이 바뀐 것이 아니라 참조하는 사실이 바뀐 것**입니다.
개정 절차(검토·승인·시행일 지정·이전본 아카이빙)를 밟을 대상이 아닙니다.

### 2-4. 변경내역 관리 실태 (문제 7 상세)

당사 제17조는 이미 다음을 **명문화**하고 있습니다.

> "당사는 개인정보 처리방침을 변경하는 경우에는 변경 및 시행의 시기, 변경된 내용을 지속적으로 공개하며
> **변경된 내용은 고객이 쉽게 확인할 수 있도록 변경 전·후를 비교하여 공개합니다.**"

그러나 이행 수단은 **신구비교표 수기 작성**입니다. 여기서 두 가지 문제가 파생됩니다.

| # | 문제 | 설명 |
|---|---|---|
| 1 | **누락이 구조적으로 가능** | 수기 비교표는 "바뀐 것을 기억해서 적는" 방식. 당사 방침은 17개조에 대형 표가 다수 포함되어 표 안의 한 행 변경은 특히 누락되기 쉬우며, **누락 여부를 검증할 수단이 없음** |
| 2 | **정보주체의 직관적 확인 곤란** | 별도 문서를 열어 전체를 훑어야 하고, "이번 개정에서 나에게 영향 있는 항목"이 한눈에 들어오지 않음 |

**타사 대비 위치** (선행 분석 9-7)

| | 토스증권 | 카카오페이증권 | **우리투자증권** |
|---|---|---|---|
| 변경내역 제공 | 별도 문서로 상시 제공 | **버전마다 `[개정내용]` 개별 링크** | 통합 링크 1개 |
| 신구대조표 | **웹 3열 표** (변경 전/후/비고) | **버전별 PDF 첨부** | 별도 신구비교표 (**수기**) |
| 변경 부분 표시 | 볼드 + 밑줄 (색상 단독 의존 없음) | 미확인 | 미확인 |
| 변경 사유 기재 | **100% 기재** (비고 셀 병합) | 미확인 | 미확인 |
| 미변경 구간 처리 | **`(중략)` 생략** | 미확인 | 미확인 |
| 요약 계층 | **없음** (처음부터 전문 대조표) | 없음 | 없음 |

**따라가야 할 것과 앞설 수 있는 것을 구분해야 합니다** (선행 분석 9-7).

| 구분 | 항목 | 당사 대응 |
|---|---|---|
| **따라가기** | 토스증권은 **모든 변경에 사유를 기재**합니다. 개정일자 한 줄만 바뀌어도 "개정일자 반영"이라고 씁니다 | **사유 필수 입력 강제** (사유 없이 승인 불가) + 대고객 노출 |
| **따라가기** | 사유를 지점마다 반복하지 않고 **하나의 사유로 여러 변경을 묶어 비고 셀을 병합**합니다 | **`ChangeSet`(변경 그룹) 계층** 도입 |
| **앞서기** | 토스증권 변경내역은 스크롤 수십 화면 분량의 **전문 대조표**뿐입니다. 정보주체가 훑기 어렵습니다 | **3계층 정보구조** (요약 → 변경 그룹 → 전문 대조) |

> **`ChangeSet`이 이 과제에서 가장 중요한 모델링 결정입니다.**
> 용어 하나를 조문 전반에서 일괄 치환하면 변경 지점이 수십 곳 생깁니다.
> 사유를 개별 변경의 속성으로 두면 같은 문장이 수십 번 반복되어 **읽을 수 없는 표**가 됩니다.
> 실제 업무와도 맞습니다 — 담당자는 "왜 고치는가"를 **건별이 아니라 사안별로** 정의합니다.

> **이 항목은 사내 설득에서 가장 방어하기 쉬운 논거입니다.**
> 새로운 의무를 만드는 것이 아니라, **제17조가 이미 선언한 의무를 시스템으로 이행**하는 것이기 때문입니다.
> 조항 단위로 저장되어 있으면 비교표는 **계산 결과**이므로 누락이 원리적으로 발생하지 않습니다.

### 2-5. 위·수탁 현황 관리 실태 (문제 8 상세)

#### 어느 문서에 고지가 필요한가

| 문서 | 위·수탁 현황 | 근거 |
|---|---|---|
| **개인정보처리방침** | **필요** | 제8조(개인정보 처리업무의 위탁)에서 참조. 「개인정보 보호법」 제26조·제30조 |
| **신용정보활용체제** | **필요** | 제3조 라.에서 *"개인(신용)정보 관련 업무 위탁·제휴현황 — 홈페이지 > 개인정보처리방침 > '…현황' 참고"* 로 **원문이 직접 참조** |
| **고객정보취급방침** | **해당 없음** | 「금융지주회사법」 제48조의2에 따른 **그룹사 간 고객정보 제공·이용** 문서. 본문에 **제공처(그룹사 목록)** 가 직접 기재되며, 제3자에게 처리를 맡기는 **위탁**과는 다른 개념. 실제 게시 원문에도 항목이 없고, **그룹 제정 문서라 당사가 추가할 수도 없음** |

> **두 문서가 같은 현황 문서를 참조**합니다. 개인정보처리방침 제8조와 신용정보활용체제 제3조 라.의 문구가 동일합니다.
> 따라서 현황은 **특정 문서의 하위가 아니라 문서 간 공유 개체**여야 합니다(5-1 참조).

#### 지금은 어떻게 게시되고 있나 — 링크는 맞지만 팝업이다

제8조 수탁업체 칸에는 `홈페이지 >` `개인정보처리방침 >` `'개인(신용)정보처리 위탁 및 제휴업체 현황' 참고`
세 개의 링크 칩이 있고 **실제로 클릭됩니다.** 다만 열리는 것이 별도 페이지가 아니라
**본문 위에 뜨는 레이어 팝업**이어서 **고유 주소가 없습니다.**

| # | 제약 | 실무상 결과 |
|---|---|---|
| 1 | **고유 URL 부재** | 민원·분쟁, 감독기관 제출 시 지목할 주소가 없음 |
| 2 | **버전을 주소로 표현 불가** | 현황 버전(g1…gN)을 각각 가리킬 수 없어 **과거 시점 현황 지목이 불가능** |
| 3 | **북마크·공유·검색·인쇄 곤란** | 「개인정보 보호법」 제26조 제2항의 **"공개"** 취지에 비추어 접근성 취약 **[확인 필요]** |
| 4 | **홈페이지 프레임 종속** | 팝업은 홈페이지 스크립트로 뜸 → 재구축 시 **현황 도달 경로 자체가 소멸** 위험 |

> **4번은 요구사항 5(홈페이지 구조 비종속)와 정면으로 충돌합니다.**
> 개선의 실질은 현황을 **고유 주소를 가진 독립 페이지**로 바꾸는 것입니다.

#### 위탁과 제휴를 나눠 관리하는 것이 적절한가 — 나누는 것이 맞습니다

게시 팝업은 한 화면에 **두 개의 표**를 담고 있습니다(위탁 20건 / 제휴 13건).

| | 위탁 표 | 제휴 표 |
|---|---|---|
| 컬럼 | 위탁업체명 / 위탁 목적 / **위탁하는** 개인(신용)정보항목 / 담당부서 | 제휴업체명 / 제공목적 / **제공하는** 개인(신용)정보의 종류 / 담당부서 |
| 근거 | 「개인정보 보호법」 **제26조** · 「신용정보법」 제17조 | 「개인정보 보호법」 **제17조** · 「신용정보법」 제32조 |
| 성격 | 수탁자가 **위탁자의 관리·감독**을 받음 | 제3자가 **자기 목적**으로 이용 |
| 정보주체 동의 | 원칙적으로 불요 — **공개**로 갈음 | **원칙적으로 필요** |

**근거 법령과 요구 절차가 다르므로 분리는 옳습니다.** 합치면 정보주체가
"동의한 제공"과 "공개로 갈음한 위탁"을 구분할 수 없게 됩니다.

**다만 배치가 어긋나 있습니다.** 당사 방침의 실제 구조는 다음과 같습니다.

```
제6조 개인정보의 제3자 제공  ──▶ 개인(신용)정보 제3자 제공 현황            (별도)
제8조 개인정보 처리업무의 위탁 ──▶ 개인(신용)정보 처리 위탁 및 제휴업체 현황 (별도)
                                    ├─ 표1 위탁 20건
                                    └─ 표2 제휴 13건   ← 성격은 제3자 제공
제9조 개인정보의 국외 수집·이전 ──▶ 개인(신용)정보 국외 이전 현황           (별도)
```

**제휴는 제3자 제공인데 제8조(위탁) 쪽 현황에 들어가 있습니다.**
정보주체가 *"내 정보가 어느 회사에 제공되는가"* 를 확인하려면 **두 곳을 봐야 하고**,
그중 하나는 **위탁 조항을 거쳐야** 합니다.

| | 지금 | 권고 |
|---|---|---|
| 표 분리 | O | **유지** |
| 문서(파일) | 한 파일에 두 표 | **분리** — 하나의 표에 하나의 법적 근거 |
| 주소 | 팝업 1개, URL 없음 | **각각 고유 URL** |
| 참조 조문 | 제8조에서 둘 다 | 위탁 → **제8조**, 제휴 → **제6조**에서도 링크 |

> 원칙: **하나의 표에 하나의 법적 근거, 하나의 조문이 자기 현황을 직접 가리킬 것.**
> 제휴를 제17조 제공으로 볼지 별도 유형으로 볼지는 준법감시 확인이 필요합니다. **[확인 필요]**

#### 팝업 표의 실제 구조 — 데이터 모델을 바꾸는 두 가지 발견

실제 게시 팝업의 컬럼은 **위탁업체명 / 위탁 목적 / 위탁하는 개인(신용)정보항목 / 담당부서** 4개입니다.

**(1) 담당부서가 공개 항목입니다.**
IT기획부·CX기획부·리테일성장실·종합금융사업추진부·영업솔루션부 등 실제 부서명이 표에 기재되어 있습니다.
**조직개편이 있으면 이 표도 갱신해야 합니다.** 요구사항 3(조직개편 = 데이터 수정)이 방침 본문뿐 아니라
**위·수탁 현황에도 적용**된다는 뜻입니다. 다만 위탁 내용은 불변이므로 **본문 검토 대상은 아닙니다.**
→ 현황의 담당부서는 `OrgMaster`와 연동되어야 합니다.

**(2) 두 표의 셀 병합 방향이 정반대입니다.**

| | 병합 대상 | 예 |
|---|---|---|
| **위탁 표** | **업체명** 셀 | 나이스평가정보 1개 업체 : 업무 2건 (담당부서도 CX기획부 / IT기획부로 상이) |
| **제휴 표** | **목적·항목·담당부서** 셀 | 펌뱅킹 1개 목적 : 신한·우리·국민은행 3개 업체 |

제휴 표에는 이런 그룹이 3개 있습니다 — 펌뱅킹(3사), 포트폴리오 추천·리밸런싱(3사), 투자자문서비스(3사).

> **데이터 단위는 "업체"가 아니라 "업체 × 목적"이고, 특정 컬럼을 그룹 키로 고정하면 안 됩니다.**
> 렌더링이 **같은 그룹 안에서 값이 같은 컬럼을 병합**해야 두 표가 하나의 코드로 재현됩니다.
> 업체 기준으로 묶으면 제휴 표를, 목적 기준으로 묶으면 위탁 표를 그릴 수 없습니다.
> 토스증권 신구대조표의 비고 셀 병합과 **같은 rowspan 패턴**입니다.
> **업체 불변키(`co`)** 와 **행 불변키(`rowKey`)** 를 분리해야 사명 변경 시 그 업체의 모든 행이 함께 갱신됩니다.

**(2-1) 전량 대조에서 결함 9건이 나왔습니다** (현황 7 · 본문 2).

#### 현황 변경은 방침 개정인가 — 재검토 결과

**결론: 방침 개정은 아니지만, 이력 관리 의무가 면제되는 것은 아닙니다.**

| # | 판단 | 근거 |
|---|---|---|
| 1 | **수탁사만 바뀌면 방침 개정이 아니다** | 당사 제8조가 수탁사 목록을 본문에 두지 않고 **"…현황 참고"로 참조**합니다. 참조 대상이 갱신될 뿐 본문이 바뀌지 않습니다 |
| 2 | **그러나 공개 의무는 그대로 남는다** | 「개인정보 보호법」 **제26조 제2항**의 위탁 업무 내용·수탁자 공개 의무는 **제30조(처리방침)와 별개**로 존재합니다. 개정 절차를 밟지 않을 뿐, **현황은 지체 없이 갱신**해야 합니다 |
| 2+ | **무엇보다 당사 방침이 스스로 고지를 약속했다** | 제8조 말미에 **"업체 변경 시 공지사항 및 개인정보처리방침을 통해 고지하겠습니다"** 라고 명시되어 있습니다. 제17조의 *"변경 전·후를 비교하여 공개"* 와 같은 구조로, **법령 이전에 방침상의 자기 구속**입니다 |
| 3 | **그래서 현황 자체의 버전·스냅샷이 필요하다** | 방침 이전본에는 수탁사 목록이 없습니다(별도 문서이므로). 현황의 시점별 스냅샷이 없으면 **"2025년 6월에 어느 수탁사에 위탁하고 있었는가"를 입증할 수 없습니다** |
| 4 | **다만 본문 검토가 필요한 경우가 있다** | 아래 |
| 5 | **담당부서만 바뀌면 조직개편이다** | 현황 버전은 올라가되 **본문 검토 대상은 아닙니다.** 요구사항 3과 같은 취급 (아래 상세) |

> **2+ 가 이 논의를 종결시킵니다.** 이력 관리가 필요한지를 따질 단계가 아니라,
> **이미 방침 본문으로 약속해 둔 것을 이행할 수단이 없는 상태**입니다.

#### 담당부서 변경은 개정인가 — 아니오, 가장 명확한 경우입니다

| # | 근거 |
|---|---|
| 1 | 「개인정보 보호법」 **제26조 제2항이 공개하도록 요구하는 것은 "위탁하는 업무의 내용"과 "수탁자"** 입니다. 담당부서는 법정 공개 항목이 아니라 **당사가 자발적으로 추가한 관리 정보**입니다 **[확인 필요 — 시행령]** |

**여기가 실무적으로 가장 아픕니다.** 등재 건수는 IT기획부 **10건**, 리테일성장실 9건,
CX기획부·자금부·디지털PB센터 각 4건입니다.
*"IT기획부 → IT본부"* 한 번이면 **워드에서 10곳**을 고쳐야 하고, 방침 본문·신용정보활용체제까지
합치면 더 늘어나며 **누락이 구조적으로 발생**합니다.

> 주의 — **담당부서와 위탁 내용이 함께 바뀌는 경우**는 본문 검토 대상입니다.
> 도구는 *"담당부서만 바뀐 변경"* 을 따로 식별해 이 경우를 구분합니다.

### 3-2. 핵심 원칙 6가지

| 원칙 | 내용 |

| **P4. 게시는 스냅샷** | 승인 시점의 상태를 동결(freeze)하여 보관. 이후 참조 데이터가 바뀌어도 과거본은 불변 |
| **P5. 변경내역은 계산 결과** | 신구대조표를 사람이 작성하지 않는다. 조항 단위 저장에서 **자동 생성**하며, 같은 기록에서 내부 감사용과 대고객 공개용 **두 개의 뷰**를 만든다 |
| **P6. 참조 데이터도 자체 버전을 가진다** | 본문에서 분리한 현황(위·수탁 등)은 **버전·기준일·스냅샷을 독립적으로** 가진다. 방침 개정이 아니어도 시점별 입증이 가능해야 하기 때문이다 |

> **P4 보충**: P3와 P4는 언뜻 충돌해 보입니다. 해결은 **"현행본은 참조, 과거본은 동결"** 입니다.
> 현행 방침은 조직 마스터를 실시간 참조하고, 새 버전을 게시하는 순간 직전 버전은
> **당시 값이 박힌 스냅샷으로 동결**됩니다. 이로써 "인사이동은 개정이 아니다"와
> "과거 특정 시점의 게시본을 그대로 증빙한다"를 동시에 만족합니다.

### 5-2. 설계 시 반드시 지킬 규칙

| # | 규칙 | 이유 |
|---|---|---|
| R1 | 조항은 **표시번호와 별개의 불변 키(`sectionKey`)** 를 가진다 | 조항 신설 시 "제7조→제8조" 이동. 번호를 키로 쓰면 이력·Diff가 전부 깨짐 |
| R2 | 표시번호는 **렌더링 시점에 자동 채번**한다 | 조항 순서 변경이 데이터 수정으로 끝남 |
| R3 | `OrgMaster`·`Registry`는 **버전에 종속되지 않는다** | 요구사항 3·4 |
| R4 | 버전 게시 시 참조 데이터를 **스냅샷으로 동결**한다 | 과거본 증빙 (P4) |
| R5 | 조항 간 참조는 **`sectionKey` 기준**으로 저장한다 | "제2조 참조" 문구가 번호 변경에 깨지지 않음 |
| R6 | 모든 게시 스냅샷은 **해시와 타임스탬프**를 함께 보관한다 | 감사·분쟁 대응 |
| R7 | `ChangeLog`의 각 필드는 **공개 여부를 명시**한다 | 대고객 변경내역에 담당자 실명·결재 정보가 새어나가면 안 됨 |
| R8 | 신구대조표는 **저장하지 않고 계산**한다 | 저장하면 본문과 어긋날 수 있음. 조항 데이터가 유일한 출처(P5) |
| R9 | 변경 사유는 **`ChangeSet`에 붙이고 개별 변경에 붙이지 않는다** | 용어 일괄 치환 시 사유가 수십 번 반복되는 것을 방지. 비고 셀 병합의 데이터 근거 |
| R10 | `OrgMaster`·`Registry`는 **모든 문서가 공유**한다. 문서별 사본을 두지 않는다 | 같은 인물·같은 현황이 여러 문서에 중복 기재되어 한쪽만 갱신되는 것을 방지 |
| R11 | 여러 문서를 함께 고치는 개정은 **하나의 `Amendment`** 로 묶는다 | 법령 개정 1건 = 문서 N개 동시 개정. 문서별로 따로 관리하면 누락이 발생 |
| R12 | `Registry`는 **자체 버전·기준일·스냅샷**을 가진다 | 방침 개정이 아니어도 「개인정보 보호법」 제26조 제2항의 공개 의무는 별개로 존재. 시점별 위탁 현황 입증에 필요 |
| R13 | 현황의 각 행(수탁사)에 **불변키**를 부여한다 | 사명 변경을 '삭제 + 신규'로 잘못 기록하는 것을 방지 |
| R14 | 국외 이전 발생·홍보 업무 위탁·업무 종류 신설은 **본문 검토 대상으로 표시**한다 | 현황 갱신만으로 끝나지 않는 변경 유형 |

### 5-3. 3사 공통 패턴이 데이터 모델을 확정한 근거

선행 분석에서 확인된 사실입니다 — **3사 모두 자주 바뀌는 표를 본문에서 분리**하고 있습니다.

| | 분리 대상 | 방식 |
|---|---|---|
| 토스증권 | 제3자 제공·추가이용·업무위탁·채용위탁·국외이전·변경내역 | `>> 링크` 6종 |
| 카카오페이증권 | 제3자 제공, 위탁·재위탁 | `(상세 내역 보기)` 링크 |
| 우리투자증권 | 위탁 및 제휴업체 현황 | 링크 3칩 → **레이어 팝업** (별도 페이지 아님) |

수탁사 한 곳이 바뀔 때마다 방침 전체를 개정할 수 없기 때문입니다.

당사도 **링크로 안내하고 있는 것은 맞습니다.** 다만 열리는 것이 별도 페이지가 아니라
**레이어 팝업(모달)** 이어서 **고유 주소가 없고**, 현황에 **기준일 표기도 없습니다.**
고유 주소가 없다는 것은 곧 **현황 버전을 주소로 가리킬 수 없다**는 뜻입니다(2-5 참조). 이번 구축에서 해소합니다.

### 5-4. 감사 로그와 대고객 변경내역의 분리

두 산출물은 **같은 `ChangeLog` 데이터에서 나오지만 노출 범위가 다릅니다.**

| | 내부 감사 로그 | 대고객 변경내역 |
|---|---|---|
| 목적 | 통제·증빙 | 정보주체 고지 |
| 포함 | 변경자, 검토자, **승인자**, 결재 일시, 초안 이력, 스냅샷 해시 | 시행일, 변경 조항, 변경 유형, **변경 사유**, 변경 전·후 |
| 제외 | — | **담당자 실명·결재 정보 노출 금지** |
| 열람 권한 | 내부 권한자 | 누구나 |

```
        ChangeLog (단일 기록)
               │
       ┌───────┴────────┐
       ▼                ▼
  내부 감사 로그    대고객 변경내역
  (전체 필드)      (공개 필드만)
```

> 이 구분을 설계 초기에 하지 않으면 나중에 **"감사 로그를 그대로 공개"** 하거나
> **"공개용을 또 수기로 만드는"** 두 가지 잘못된 선택지만 남습니다.

| 5 | **관리 데이터** | 조직 마스터 편집 → 본문 즉시 반영 (개정 절차 미발생) | 3 |
| 6 | **변경내역 (대고객)** | 정보주체가 보는 화면. 버전별 변경 요약 + 변경 조항 칩 + 변경 사유. 결재 정보는 노출하지 않음 | 1 |
| 7 | **인계 파일 내보내기** | 승인된 본문을 개발팀 인계용 단일 HTML로 생성. 현황 표는 별도 파일로 분리 | 5 |
| 8 | **조항 편집** | 조항 단위 편집 + 변경 사유 입력. 저장 시 변경 조항·사유가 자동 정리 | 1, 6 |
| 9 | **결재 · 데이터** | 작업자 등록, 작성→검토→승인 단계 전환, 편집 이력(Audit Log), 데이터 저장·불러오기 | 1 |
| — | **스킨 전환** | 동일 콘텐츠를 서로 다른 홈페이지 껍데기에 얹어 독립성 실증 | 5 |

**변경내역 정보구조 3계층** — 토스증권은 3계층부터 시작해 훑기 어렵습니다. 당사는 1계층부터 제공합니다.

```
1계층  변경 요약        한 문장 요약 + 신설/수정/삭제 건수              ← 화면 6 상단
2계층  변경 그룹 카드    ChangeSet 단위 (사유 · 영향 조항 · 변경 유형)    ← 화면 6 본문
3계층  전문 신구대조표   좌우 병렬 3열 + 비고 셀 병합 + (중략) 생략       ← 화면 4
```

| 변경 사유 | 기록·공개 안 됨 | **필수 입력 + 대고객 공개** |

> 정보보호부가 최종 HTML을 생성해 넘기고 개발팀은 파일만 교체하는 방식으로,
> **게시 반영 구간의 리드타임과 오탈자 문제를 예산 없이 해소**합니다.
> 산출물 구조를 본 기획안의 스냅샷 규격과 동일하게 설계했으므로, 이후 CMS 구축 시 버릴 것이 없습니다.

| 단계 | 내용 | 산출물 |
|---|---|---|
| **0단계 (선행)** | **정본 확정 및 사본 전수조사** — 방침이 게시된 모든 위치(도메인·앱·PDF·내부문서) 목록화, 내용 일치 여부 대조 | 사본 현황표 = 이관 범위이자 As-Is 근거자료 |

### B-3. 정정 후 잔여 확인 사항

정정안을 모두 적용해도 **정합성 점검에 3건이 남습니다.** 판단이 필요한 항목이기 때문입니다.

| 잔여 항목 | 성격 | 판단 필요 사항 |
|---|---|---|
| 우리은행이 위탁·제휴 양쪽에 등재 | 정보 | 한 회사가 두 법적 지위를 갖는 것은 정상. 표를 분리 게시하면 구분됨 |
| 우리카드가 위탁·제휴 양쪽에 등재 | 정보 | 〃 |
| "투자권유대행인"이 집합적 지칭 | 권고 | F5 적용 후에도 특정 상호가 아님. **협회 조회 경로 병기 여부 판단 필요** **[확인 필요]** |

> **이것이 정합성 점검의 설계 의도입니다.** 자동으로 없앨 수 있는 것과
> **사람이 판단해야 하는 것**을 구분해서 남깁니다. 전부 사라지는 것이 목표가 아닙니다.
