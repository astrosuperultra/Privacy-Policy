# 개인정보처리방침 관리체계 개선 기획안

- 작성일: 2026-08-12
- 소관: 정보보호부
- 선행 문서: `docs/01-benchmark-3사-구조비교.md` (토스증권·카카오페이증권·당사 구조 비교 분석)

---

## 1. 추진 배경 및 목표

### 1-1. 한 줄 정의

> **개인정보처리방침을 "문서(Document)"가 아니라 "구조화된 데이터(Content)"로 관리하고,
> 대고객 홈페이지와 분리된 독립 관리체계를 구축한다.**

### 1-2. 배경

선행 분석(3사 벤치마킹) 결과, 당사 개인정보처리방침은 다음 상태입니다.

| 관점 | 진단 |
|---|---|
| **콘텐츠 품질** | **양호** — 라벨링 20종, 제정일/시행일/최근개정일 3단 구분, 이전본 적용기간 명시. **3사 중 가장 정교** |
| **관리 방식** | **취약** — 위 체계를 전부 수작업으로 유지. 개정 시 개발·빌드·배포 필요 |
| **게시 구조** | **취약** — 화면 ID + 탭 번호로만 식별. 버전이 URL에 없음. 도메인별 사본 존재 |

즉 **이 과제는 부실한 문서를 고치는 일이 아니라, 이미 잘 정의된 체계를 시스템화하는 일**입니다.

### 1-3. 문제의 정량적 근거

| | 토스증권 | 카카오페이증권 | **우리투자증권** |
|---|---|---|---|
| 연평균 개정 횟수 | 5.7회 | 2.2회 | **0.7회** |
| 2026년 개정 횟수 | **10회** | 1회 | **1회** |
| 최근 개정일 | 2026-08-11 | 2026-05-29 | 2026-03-12 |

토스증권은 2026-05-11 / 05-13 / 05-20 / 05-21, **열흘 사이 네 번** 개정했습니다.
정기 개정으로 설명되지 않는 빈도이며, 오탈자·문구·링크 수준을 **발견 즉시 반영**한다는 의미입니다.

반면 당사는 개정 리드타임이 길어 소규모 수정이 누적·지연됩니다. 실제로 현행 방침에는 다음이 남아 있습니다.

- 제12조: "**당행** 앱 이용자의 행태정보 분석을 위해" — 증권사 방침에 은행 표현
- 제6조: "납치, **감긍** 등 범죄" — 오타
- 제15조: 경찰청 사이버안전국 구 URL 사용 가능성 (`cyberbureau.police.go.kr`)

이는 담당자 역량 문제가 아니라 **구조 문제**입니다. 문구 하나 고치는 데 개발 배포가 필요하면,
그런 수정은 "다음 정기 개정 때 함께"로 밀리고 그대로 수년이 지납니다.

### 1-4. 목표

| # | 목표 | 측정 지표 |
|---|---|---|
| 1 | 개정 리드타임 단축 | 문구 수정 기준 **수일 → 당일** |
| 2 | 대고객 게시 정본 일원화 | 게시 위치 **N개소 → 1개소 참조** |
| 3 | 개정 이력 증빙체계 확보 | 버전별 **영구 URL + 스냅샷 해시** 보유율 100% |
| 4 | 홈페이지 재구축 영향도 제거 | 방침 관리 시스템의 **홈페이지 의존도 0** |
| 5 | 조직 변경의 개정 유발 제거 | 인사이동 시 **개정 절차 0회** |
| 6 | **변경내역 자동화 및 대고객 공개** | 신구비교표 **수기 작성 0건** / 버전별 변경내역 공개율 100% |

## 2. As-Is 현황 진단

### 2-1. 현행 업무 흐름

```
정보보호부                         홈페이지 담당부서        개발
   │                                    │                  │
Word/Excel 수정 ──▶ 검토 ──▶ PDF 변환 ──▶ 반영 요청 ──▶ 소스 수정 ──▶ 빌드 ──▶ 배포 ──▶ 확인
                              │
                          이전본 PDF 별도 보관
```

### 2-2. 구조적 문제 6가지

| # | 문제 | 영향 |
|---|---|---|
| 1 | **정본이 복수로 존재** (도메인별 사본 + PDF + 내부 Word) | 개정 시 일부 누락 → 서로 다른 방침이 동시 게시 |
| 2 | **버전이 데이터가 아니라 파일로 관리** (`privacy2.do`, `privacy3.do`) | 특정 시점 방침 특정 곤란 → 분쟁·감독 대응 시 입증 비용 |
| 3 | **과거본에 영구 링크 없음** | 인용·비교·검색 불가 |
| 4 | **콘텐츠 수정이 개발 배포에 종속** | 리드타임 + 법정 시행일 준수 리스크 |
| 5 | **조항 단위 관리 불가** | 제7조만 바뀌어도 전체 재생성. 변경 사유가 데이터로 남지 않음 |
| 6 | **조직 정보가 본문에 하드코딩** | 인사이동마다 개정 절차 전체 재수행 |
| 7 | **변경내역(신구비교표)을 수기로 작성** | 누락이 구조적으로 가능하고 검증 수단 없음. 정보주체가 변경 내용을 직관적으로 확인 곤란 |

### 2-3. 조직 정보 하드코딩 실태 (문제 6 상세)

현행 방침에 다음 정보가 **본문에 직접 기재**되어 있습니다.

| 위치 | 내용 | 변경 빈도 |
|---|---|---|
| 제14조 | CPO 직위·성명 (상무 황돈구) | 인사이동 시 |
| 제14조 | 개인정보 보호업무 부서 (정보보호부) | 조직개편 시 |
| 제14조 | 고충처리 부서 (금융소비자보호부) | 조직개편 시 |
| 제16조 | CCTV 관리책임자 (HR지원부장) | 조직개편 시 |
| 제16조 | **접근권한자 2인의 실명 + 직통번호** | **인사이동 시 (가장 빈번)** |
| 제16조 | CCTV 설치 대수(65대), 설치 지점 | 점포 신설·폐쇄 시 |

→ 이들은 **방침의 내용이 바뀐 것이 아니라 참조하는 사실이 바뀐 것**입니다.
개정 절차(검토·승인·시행일 지정·이전본 아카이빙)를 밟을 대상이 아닙니다.

### 2-4. 변경내역 관리 실태 (문제 7 상세)

당사 제17조는 이미 다음을 **명문화**하고 있습니다.

> "당사는 개인정보 처리방침을 변경하는 경우에는 변경 및 시행의 시기, 변경된 내용을 지속적으로 공개하며
> **변경된 내용은 고객이 쉽게 확인할 수 있도록 변경 전·후를 비교하여 공개합니다.**"

그러나 이행 수단은 **신구비교표 수기 작성**입니다. 여기서 두 가지 문제가 파생됩니다.

| # | 문제 | 설명 |
|---|---|---|
| 1 | **누락이 구조적으로 가능** | 수기 비교표는 "바뀐 것을 기억해서 적는" 방식. 당사 방침은 17개조에 대형 표가 다수 포함되어 표 안의 한 행 변경은 특히 누락되기 쉬우며, **누락 여부를 검증할 수단이 없음** |
| 2 | **정보주체의 직관적 확인 곤란** | 별도 문서를 열어 전체를 훑어야 하고, "이번 개정에서 나에게 영향 있는 항목"이 한눈에 들어오지 않음 |

**타사 대비 위치** (선행 분석 9-7)

| | 토스증권 | 카카오페이증권 | **우리투자증권** |
|---|---|---|---|
| 변경내역 제공 | 별도 문서로 상시 제공 | **버전마다 `[개정내용]` 개별 링크** | 통합 링크 1개 |
| 신구대조표 | **웹 3열 표** (변경 전/후/비고) | **버전별 PDF 첨부** | 별도 신구비교표 (**수기**) |
| 변경 부분 표시 | 볼드 + 밑줄 (색상 단독 의존 없음) | 미확인 | 미확인 |
| 변경 사유 기재 | **100% 기재** (비고 셀 병합) | 미확인 | 미확인 |
| 미변경 구간 처리 | **`(중략)` 생략** | 미확인 | 미확인 |
| 요약 계층 | **없음** (처음부터 전문 대조표) | 없음 | 없음 |

**따라가야 할 것과 앞설 수 있는 것을 구분해야 합니다** (선행 분석 9-7).

| 구분 | 항목 | 당사 대응 |
|---|---|---|
| **따라가기** | 토스증권은 **모든 변경에 사유를 기재**합니다. 개정일자 한 줄만 바뀌어도 "개정일자 반영"이라고 씁니다 | **사유 필수 입력 강제** (사유 없이 승인 불가) + 대고객 노출 |
| **따라가기** | 사유를 지점마다 반복하지 않고 **하나의 사유로 여러 변경을 묶어 비고 셀을 병합**합니다 | **`ChangeSet`(변경 그룹) 계층** 도입 |
| **앞서기** | 토스증권 변경내역은 스크롤 수십 화면 분량의 **전문 대조표**뿐입니다. 정보주체가 훑기 어렵습니다 | **3계층 정보구조** (요약 → 변경 그룹 → 전문 대조) |

> **`ChangeSet`이 이 과제에서 가장 중요한 모델링 결정입니다.**
> 용어 하나를 조문 전반에서 일괄 치환하면 변경 지점이 수십 곳 생깁니다.
> 사유를 개별 변경의 속성으로 두면 같은 문장이 수십 번 반복되어 **읽을 수 없는 표**가 됩니다.
> 실제 업무와도 맞습니다 — 담당자는 "왜 고치는가"를 **건별이 아니라 사안별로** 정의합니다.

> **이 항목은 사내 설득에서 가장 방어하기 쉬운 논거입니다.**
> 새로운 의무를 만드는 것이 아니라, **제17조가 이미 선언한 의무를 시스템으로 이행**하는 것이기 때문입니다.
> 조항 단위로 저장되어 있으면 비교표는 **계산 결과**이므로 누락이 원리적으로 발생하지 않습니다.

## 3. To-Be 목표 모델

### 3-1. 개선 후 업무 흐름

```
정보보호부
   │
조항 단위 수정 ──▶ 검토 ──▶ 승인 ──▶ 게시(즉시/예약)
                                          │
                          ┌───────────────┼───────────────┐
                          ▼               ▼               ▼
                      버전 스냅샷     채널 자동 반영     PDF 자동 생성
                      + 해시 보관    (홈페이지/앱)
```

### 3-2. 핵심 원칙 4가지

| 원칙 | 내용 |
|---|---|
| **P1. 원본은 데이터** | HTML/PDF는 산출물. 원본은 CMS DB의 구조화 데이터 |
| **P2. 조항이 단위** | 문서 전체가 아니라 조항(Section)이 편집·이력·참조의 단위 |
| **P3. 변하는 것은 분리** | 조직 정보, 위·수탁 현황 등 자주 바뀌는 데이터는 본문에서 분리 |
| **P4. 게시는 스냅샷** | 승인 시점의 상태를 동결(freeze)하여 보관. 이후 참조 데이터가 바뀌어도 과거본은 불변 |
| **P5. 변경내역은 계산 결과** | 신구대조표를 사람이 작성하지 않는다. 조항 단위 저장에서 **자동 생성**하며, 같은 기록에서 내부 감사용과 대고객 공개용 **두 개의 뷰**를 만든다 |

> **P4 보충**: P3와 P4는 언뜻 충돌해 보입니다. 해결은 **"현행본은 참조, 과거본은 동결"** 입니다.
> 현행 방침은 조직 마스터를 실시간 참조하고, 새 버전을 게시하는 순간 직전 버전은
> **당시 값이 박힌 스냅샷으로 동결**됩니다. 이로써 "인사이동은 개정이 아니다"와
> "과거 특정 시점의 게시본을 그대로 증빙한다"를 동시에 만족합니다.

## 4. 시스템 구성도

```
┌─────────────────────────────────────────────────────────┐
│                  내부망 (정보보호부)                     │
│  ┌───────────────────────────────────────────────────┐  │
│  │        개인정보처리방침 관리시스템 (CMS)          │  │
│  │                                                   │  │
│  │  조항 편집 · 버전/스냅샷 · 승인 워크플로          │  │
│  │  조직 마스터 · 위수탁 레지스트리 · Audit Log      │  │
│  │  예약 게시 · 자동 신구대조표 · PDF Export         │  │
│  └───────────────────────┬───────────────────────────┘  │
└──────────────────────────┼──────────────────────────────┘
                           │  승인·게시 시점 1회 푸시
                           │  (실시간 API 호출 아님)
                           ▼
              ┌────────────────────────────┐
              │  정적 스냅샷 저장소 (DMZ)   │
              │  HTML / JSON / PDF          │
              │  + 해시 + 타임스탬프        │
              └─────────────┬──────────────┘
                            │  읽기 전용
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
    대고객 홈페이지      펀드슈퍼마켓        모바일 앱(웹뷰)
```

### 4-1. 배포 방식을 "실시간 API"가 아닌 "게시 시점 푸시"로 하는 이유

| 항목 | 실시간 API 호출 | **게시 시점 스냅샷 푸시 (채택)** |
|---|---|---|
| 망분리·보안심의 | DMZ→내부망 상시 연결 필요, 심의 통과 곤란 | 단방향 푸시, 상시 연결 불필요 |
| 가용성 | CMS 장애 = 대고객 화면 장애 | CMS 장애와 무관하게 게시 유지 |
| 증빙 | 시점별 게시본 재현 곤란 | **스냅샷 + 해시로 무결성 증빙** |
| 성능 | 조회마다 백엔드 부하 | 정적 파일, CDN 캐싱 가능 |

## 5. 데이터 모델

### 5-1. 개체 구조

```
Policy (방침)
  code = "privacy-policy"          ← 불변. 대외 고정 URL의 근거
  │
  ├─ PolicyVersion (버전)
  │     versionNo, 시행일, 종료일, 상태, 개정사유,
  │     스냅샷 해시, 게시일시, 승인자
  │     │
  │     └─ Section (조항)
  │           sectionKey (UUID, 불변)   ← 표시번호와 분리
  │           displayNo (자동 채번)
  │           labels[]                  ← 라벨링 20종 연동
  │           title, body, tables[]
  │           │
  │     │
  │     └─ ChangeSet (변경 그룹)                 ← 사유 1건 : 변경 N건. 비고 셀 병합의 근거
  │           reason (변경 사유, 필수)
  │           └─ Change (개별 변경)
  │                 sectionKey, 변경유형(ADDED/MODIFIED/REMOVED),
  │                 before, after, 컨텍스트 생략 여부
  │
  │           ※ 공개/비공개 필드 분리 (요구사항 1)
  │             [공개]   변경유형, 변경사유, before/after, 시행일
  │             [비공개] 변경자, 검토자, 승인자, 결재일시, 초안 이력
  │
  ├─ OrgMaster (조직 마스터)          ← 요구사항 3. 버전과 독립
  │     CPO, 보호업무 부서, 고충처리 부서, 대표번호, 이메일,
  │     CCTV 관리책임자·접근권한자·설치현황
  │
  └─ Registry (현황 레지스트리)        ← 요구사항 4. 버전과 독립
        ├─ 위·수탁 현황   (기준일 보유)
        ├─ 제3자 제공 현황 (기준일 보유)
        ├─ 국외 이전 현황  (기준일 보유)
        └─ 제휴업체 현황   (기준일 보유)
```

### 5-2. 설계 시 반드시 지킬 규칙

| # | 규칙 | 이유 |
|---|---|---|
| R1 | 조항은 **표시번호와 별개의 불변 키(`sectionKey`)** 를 가진다 | 조항 신설 시 "제7조→제8조" 이동. 번호를 키로 쓰면 이력·Diff가 전부 깨짐 |
| R2 | 표시번호는 **렌더링 시점에 자동 채번**한다 | 조항 순서 변경이 데이터 수정으로 끝남 |
| R3 | `OrgMaster`·`Registry`는 **버전에 종속되지 않는다** | 요구사항 3·4 |
| R4 | 버전 게시 시 참조 데이터를 **스냅샷으로 동결**한다 | 과거본 증빙 (P4) |
| R5 | 조항 간 참조는 **`sectionKey` 기준**으로 저장한다 | "제2조 참조" 문구가 번호 변경에 깨지지 않음 |
| R6 | 모든 게시 스냅샷은 **해시와 타임스탬프**를 함께 보관한다 | 감사·분쟁 대응 |
| R7 | `ChangeLog`의 각 필드는 **공개 여부를 명시**한다 | 대고객 변경내역에 담당자 실명·결재 정보가 새어나가면 안 됨 |
| R8 | 신구대조표는 **저장하지 않고 계산**한다 | 저장하면 본문과 어긋날 수 있음. 조항 데이터가 유일한 출처(P5) |
| R9 | 변경 사유는 **`ChangeSet`에 붙이고 개별 변경에 붙이지 않는다** | 용어 일괄 치환 시 사유가 수십 번 반복되는 것을 방지. 비고 셀 병합의 데이터 근거 |

### 5-3. 3사 공통 패턴이 데이터 모델을 확정한 근거

선행 분석에서 확인된 사실입니다 — **3사 모두 자주 바뀌는 표를 본문에서 분리**하고 있습니다.

| | 분리 대상 | 방식 |
|---|---|---|
| 토스증권 | 제3자 제공·추가이용·업무위탁·채용위탁·국외이전·변경내역 | `>> 링크` 6종 |
| 카카오페이증권 | 제3자 제공, 위탁·재위탁 | `(상세 내역 보기)` 링크 |
| 우리투자증권 | 위탁 및 제휴업체 현황 | **텍스트 경로 안내** (링크 아님) |

수탁사 한 곳이 바뀔 때마다 방침 전체를 개정할 수 없기 때문입니다.
다만 당사만 **클릭 가능한 링크가 아니고, 현황 문서에 기준일 표기도 없습니다.** 이번 구축에서 해소합니다.

### 5-4. 감사 로그와 대고객 변경내역의 분리

두 산출물은 **같은 `ChangeLog` 데이터에서 나오지만 노출 범위가 다릅니다.**

| | 내부 감사 로그 | 대고객 변경내역 |
|---|---|---|
| 목적 | 통제·증빙 | 정보주체 고지 |
| 포함 | 변경자, 검토자, **승인자**, 결재 일시, 초안 이력, 스냅샷 해시 | 시행일, 변경 조항, 변경 유형, **변경 사유**, 변경 전·후 |
| 제외 | — | **담당자 실명·결재 정보 노출 금지** |
| 열람 권한 | 내부 권한자 | 누구나 |

```
        ChangeLog (단일 기록)
               │
       ┌───────┴────────┐
       ▼                ▼
  내부 감사 로그    대고객 변경내역
  (전체 필드)      (공개 필드만)
```

> 이 구분을 설계 초기에 하지 않으면 나중에 **"감사 로그를 그대로 공개"** 하거나
> **"공개용을 또 수기로 만드는"** 두 가지 잘못된 선택지만 남습니다.

```
/privacy-policy/changes/{versionId} 해당 개정의 변경내역 (개별 링크, 카카오페이증권 방식)
/privacy-policy/diff/{from}/{to}    자동 신구대조표 (변경 전·후 대조)
/privacy-policy/registry/outsourcing  위·수탁 현황 (기준일 보유)
/privacy-policy/registry/thirdparty   제3자 제공 현황
/privacy-policy/registry/overseas     국외 이전 현황
/privacy-policy/summary             알기쉬운 처리방침 (동일 버전의 다른 뷰)
/privacy-policy.pdf                 현행본 PDF (자동 생성)
```

**핵심**: `/privacy-policy` 하나만 대외 공식 주소로 삼고, 모든 채널이 이를 참조합니다.
도메인별 사본은 오픈과 동시에 **폐기 또는 리다이렉트**합니다.

| 3 | **버전 이력** | 스냅샷 목록(시행기간·상태·해시) + 작성/검토/승인/게시 감사 타임라인 | 1, 2 |

**변경내역 정보구조 3계층** — 토스증권은 3계층부터 시작해 훑기 어렵습니다. 당사는 1계층부터 제공합니다.

```
1계층  변경 요약        한 문장 요약 + 신설/수정/삭제 건수              ← 화면 6 상단
2계층  변경 그룹 카드    ChangeSet 단위 (사유 · 영향 조항 · 변경 유형)    ← 화면 6 본문
3계층  전문 신구대조표   좌우 병렬 3열 + 비고 셀 병합 + (중략) 생략       ← 화면 4
```
| — | **스킨 전환** | 동일 콘텐츠를 서로 다른 홈페이지 껍데기에 얹어 독립성 실증 | 5 |

| 원본 | Word / Excel | 구조화 데이터 (CMS DB) |
| 수정 단위 | 문서 전체 | **조항 단위** |
| 문구 수정 리드타임 | 수일 (개발·빌드·배포) | **당일 (승인 절차 기준)** |
| 버전 관리 | 파일명 / 폴더 (`privacy2.do`) | **시스템 자동 + 영구 URL** |
| 과거본 | PDF 수동 생성·보관 | **스냅샷 자동 아카이브 + 해시** |
| 변경 이력 | PDF 육안 비교 | **자동 신구대조표 (계산 결과, 누락 불가)** |
| 신구비교표 작성 | **수기 작성** (누락 검증 불가) | **자동 생성 (작성 0건)** |
| 정보주체의 변경 확인 | 별도 문서 전체 열람 | **3계층 (요약 → 조항 카드 → 전문 대조)** |
| 신구대조표 형태 | 별도 문서 (수기) | **웹 좌우 병렬 3열 + 부분 하이라이트** |
| 변경 사유 | 기록·공개 안 됨 | **필수 입력 + 대고객 공개** |
| 조직 변경 | 방침 개정 절차 전체 수행 | **데이터 수정 (개정 미발생)** |
| 위수탁 현황 | 텍스트 경로 안내, 기준일 없음 | **링크 + 기준일 보유, 독립 갱신** |
| 게시 채널 | 도메인별 개별 반영 | **단일 정본 참조** |
| 시행일 | 수동 게시 | **예약 게시** |
| 홈페이지 재구축 영향 | 방침 페이지 재개발 필요 | **무영향** |
| 관여 부서 | 정보보호부 + 홈페이지 + 개발 | **정보보호부 중심** |

## 11. 추진 계획

> **[2026-08-12 추가] 0단계와 병행 가능한 선행 조치가 있습니다.**
> 홈페이지 재구축 사업 일정이 불확실한 상황에서, **별도 발주 없이 지금 구조에서 즉시 적용 가능한 방식**을
> `docs/03-HTML-인계방식-설계서.md` 로 분리했습니다.
> 정보보호부가 최종 HTML을 생성해 넘기고 개발팀은 파일만 교체하는 방식으로,
> **게시 반영 구간의 리드타임과 오탈자 문제를 예산 없이 해소**합니다.
> 산출물 구조를 본 기획안의 스냅샷 규격과 동일하게 설계했으므로, 이후 CMS 구축 시 버릴 것이 없습니다.

| 단계 | 내용 | 산출물 |
|---|---|---|
| **0단계 (선행)** | **정본 확정 및 사본 전수조사** — 방침이 게시된 모든 위치(도메인·앱·PDF·내부문서) 목록화, 내용 일치 여부 대조 | 사본 현황표 = 이관 범위이자 As-Is 근거자료 |
| **1단계** | CMS 구축 — 조항 편집, 버전/스냅샷, 조직 마스터, 레지스트리, 승인 워크플로, Audit Log, PDF 생성 | 관리자 시스템 |
| **2단계** | 채널 연계 — 스냅샷 배포, 버전 영구 URL, 이력·Diff 대고객 공개, 예약 게시, 사본 폐기/리다이렉트 | 대고객 게시 구조 |
| **3단계** | 고지사항 통합 — 동의서, 제3자 제공 현황, 신용정보 활용체제 등으로 확대 | 고지사항 통합 관리 |

> **1단계만 완료하면 담당자 업무는 편해지지만 대외 게시 구조의 취약점은 그대로**입니다.
> 실질적 리스크 해소는 2단계에서 발생합니다.

## 부록. 선행 분석 요약

상세 내용은 `docs/01-benchmark-3사-구조비교.md` 참조.

- 3사 게시 아키텍처: 토스증권 = 콘텐츠 레지스트리(3세대) / 카카오페이증권 = 게시판형 CMS(2세대) / 당사 = 화면 하드코딩(1세대)
- 조문 구성: 토스 18조 / 카카오페이 15조 / 당사 17조 — 필수 기재사항 골격은 동일
- 당사 우위: 라벨링 20종, 제정일/시행일/최근개정일 3단 구분, 이전본 적용기간 명시 (모두 당사만 보유)
- 3사 공통: 자주 바뀌는 표를 본문에서 분리 → 본 기획의 `Registry` 개체 설계 근거
- 업계 선례: 카카오페이증권은 HTML 본문과 PDF를 병행 제공하고 버전별 신구대조표 PDF를 첨부
- 변경내역: 3사 모두 제공하나 형태가 다름. 카카오페이증권이 가장 충실(버전별 `[개정내용]` 개별 링크 + 신구대조표 PDF).
  당사는 제17조에 "변경 전·후를 비교하여 공개"를 **명문화했으나 이행 수단이 수기 작성**
- 토스증권 신구대조표 형식(캡처 확인): 웹 3열 표(변경 전/변경 후/비고), 좌우 병렬, 볼드+밑줄 강조,
  신설·삭제는 한쪽 셀 공란, 미변경 구간은 `(중략)` 생략
- **사유는 100% 기재**하되 하나의 사유로 여러 변경을 묶어 **비고 셀을 병합**. → `ChangeSet` 모델의 근거
- 다만 **요약 계층이 없어** 전문 대조표를 통째로 훑어야 하며, 이 지점은 당사가 앞설 수 있음
