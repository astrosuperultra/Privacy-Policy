## 1. 이 문서의 위치

기획안(`docs/02`)은 **시스템을 구축하는 것을 전제**한 To-Be 모델입니다.
본 문서는 그 이전에, **별도 개발 발주 없이 지금 구조에서 바로 실행 가능한 구간**만 떼어낸 실행 설계입니다.

| | 기획안 (`docs/02`) | **본 설계서 (`docs/03`)** |
|---|---|---|
| 전제 | CMS 구축 (발주 또는 자체 개발) | **기존 홈페이지 구조 유지** |
| 개발팀 작업 | 시스템 연계 개발 | **파일 교체** |
| 필요 예산 | 구축비 | **없음 (협의만 필요)** |
| 실행 시점 | 예산·발주 이후 | **즉시** |
| 홈페이지 재구축과의 관계 | 재구축과 별개로 구축 | **재구축 시 그대로 이관** |

> 본 설계서의 방식을 먼저 적용하고, 이후 여건이 되면 기획안의 CMS로 확장하는 경로가 자연스럽습니다.
> 두 단계 사이에 **버리는 산출물이 없습니다** — 인계 파일 구조가 그대로 CMS의 스냅샷 출력 규격이 됩니다.

## 2. 현행과 개선안

### 2-1. 현행

```
정보보호부                              개발팀
    │                                     │
Word/PDF 작성 ──▶ 문서 전달 ──▶ 홈페이지 프레임 내 텍스트를
                                 한 줄씩 직접 수정 ──▶ 빌드 ──▶ 배포 ──▶ 확인
                                        ▲
                              여기서 오탈자·누락 발생
```

**문제의 핵심은 "사람이 텍스트를 다시 타이핑한다"는 것**입니다.
정보보호부가 검토·승인을 마친 최종 문안이, 개발팀 손을 거치며 다시 입력되는 구간에서 원본과 달라질 수 있습니다.

### 2-2. 개선안

```
정보보호부                              개발팀
    │                                     │
조항 수정 ──▶ HTML 생성 ──▶ 파일 전달 ──▶ 파일 교체 ──▶ 배포 ──▶ 확인
              (관리 콘솔)                     ▲
                                     타이핑 구간 없음
```

**개발팀은 파일을 갈아끼울 뿐 내용을 건드리지 않습니다.** 오탈자가 발생할 구간 자체가 사라집니다.

### 2-3. 정확히 무엇이 줄어드는가

> **"배포가 없어진다"가 아닙니다.** 파일을 서버에 올리는 것도 배포 절차입니다.

| | 현행 | 개선 |
|---|---|---|
| 소스 코드 수정 | **필요** | 불필요 |
| 텍스트 재입력 | **필요 (오류 지점)** | **불필요** |
| 빌드 | 필요 | 조건부 (4-3 참조) |
| 배포 | 필요 | 필요 |
| 개발팀 검수 부담 | 문안 대조 필요 | 파일 교체 확인만 |

개발팀과 협의할 때는 이 표로 설명하는 편이 정확합니다. "개발이 없어진다"고 하면 반발이 생기지만,
**"텍스트 타이핑 작업이 없어진다"** 는 개발팀에게도 반가운 변화입니다.

## 3. 파일 구조

### 3-1. 파일 세트

본문 하나만 교체하면 **변경내역과 이전본은 여전히 수기로 남습니다.** 세트로 넘겨야 합니다.

| 파일명 | 내용 | 갱신 시점 |
|---|---|---|
| `privacy-policy.html` | 현행본 본문 | 개정 시 |
| `privacy-policy-history.html` | 이전 방침 목록 (버전·적용기간·개정 사유) | 개정 시 |
| `privacy-policy-changes.html` | 변경내역 (개정 건별 사유·변경 조항) | 개정 시 |
| `privacy-policy-diff-{이전}-{이후}.html` | 신구대조표 (좌우 병렬 3열) | 개정 시 신규 추가 |
| `privacy-policy-registry-outsourcing.html` | 위·수탁 현황 | **본문과 무관하게 수시** |
| `privacy-policy-{버전}.html` | 이전본 각각 | 개정 시 직전본 1개 추가 |

> **위·수탁 현황은 본문과 갱신 주기가 다릅니다.** 수탁사 한 곳이 바뀔 때 본문 개정 절차를 밟을 수는 없으므로,
> 이 파일만 단독 교체가 가능해야 합니다. 파일을 분리하는 이유가 여기 있습니다.

### 3-2. 파일 형태 — 본문 조각 vs 독립 페이지

| | **본문 조각 (권장)** | 독립 페이지 |
|---|---|---|
| 구조 | `<div class="pp-doc">…</div>` 만 | `<!doctype html>` 부터 전체 |
| 삽입 방식 | 기존 화면에서 include | 별도 URL로 직접 노출 |
| 프레임(GNB·탭·푸터) | 기존 화면 것 사용 | 없음 |
| 용도 | 홈페이지 본문 영역 | 팝업·인쇄·직접 링크 |

**본문 조각을 기본으로 하고, 독립 페이지는 필요 시 병행 생성**합니다.
관리 콘솔에서 두 형태를 모두 생성할 수 있습니다.

### 3-3. 삽입 방식

```
[기존 화면]  FMC5010001/main.jsp
   ├─ GNB / 탭 / 브레드크럼        ← 개발팀 소유, 그대로 유지
   ├─ <본문 영역>
   │     └─ include "/static/policy/privacy-policy.html"   ← 이 파일만 교체
   └─ 푸터                          ← 개발팀 소유, 그대로 유지
```

| 방식 | 평가 |
|---|---|
| **서버 사이드 include (권장)** | JSP `<jsp:include>` 또는 SSI. 검색엔진 노출 정상, JS 미동작 환경에서도 표시됨 |
| 클라이언트 `fetch` 후 삽입 | **권장하지 않음.** JS 미동작 시 방침이 표시되지 않음 → 법정 공개 의무 관점에서 위험 |
| `iframe` | 분리도는 높으나 높이 조절·인쇄·접근성·검색 노출에 문제 |

## 4. 반드시 먼저 정할 것

### 4-1. 스타일 소유권 — 가장 중요한 결정

정하지 않으면 **인계할 때마다 스타일 협의가 붙고, 결국 개발팀이 파일을 다시 손대게 되어 개선 효과가 사라집니다.**

| | 방식 A — 홈페이지 CSS 사용 | **방식 B — 파일에 스타일 포함 (권장)** |
|---|---|---|
| 파일 구성 | 마크업만 | 마크업 + `<style>` |
| 정보보호부 | 지정된 클래스만 사용해야 함 | 신경 쓸 것 없음 |
| 개발팀 | 사용 가능 클래스 목록을 확정·유지해야 함 | 없음 |
| 프레임과 일체감 | 완전히 동일 | 폰트·색이 약간 다를 수 있음 |
| **홈페이지 재구축 시** | **클래스 체계가 바뀌면 깨짐** | **무영향** |

> **B를 권장합니다.** 이 과제의 목표가 *"재구축에 영향받지 않는 분리"* 인데,
> 홈페이지 CSS 클래스에 의존하면 재구축 시 그 목표가 그대로 깨집니다.
> 재구축이 끝나고 안정화된 뒤 A로 통합하는 순서가 안전합니다.

**클래스 충돌 방지**: 생성되는 모든 클래스에 `pp-` 접두사를 붙입니다.
(`pp-doc`, `pp-sec`, `pp-title` …) 기존 홈페이지 스타일과 이름이 겹치지 않습니다.

### 4-2. 파일 경로 고정

```
/static/policy/
   ├─ privacy-policy.html
   ├─ privacy-policy-history.html
   ├─ privacy-policy-changes.html
   ├─ privacy-policy-diff-v7-v8.html
   └─ privacy-policy-registry-outsourcing.html
```

경로가 고정되면 이후 인계는 **항상 같은 폴더 교체**입니다. 개발팀 작업이 절차화됩니다.

### 4-3. 형상관리 포함 여부 — 리드타임을 더 줄일 수 있는 지점

| | 형상관리 포함 | 형상관리 제외 |
|---|---|---|
| 반영 절차 | 커밋 → 빌드 → 배포 | **파일 업로드만** |
| 이력 추적 | Git 이력 | 관리 콘솔 이력으로 대체 |
| 리드타임 | 배포 주기에 종속 | **즉시** |

방침 파일은 애플리케이션 로직이 아니므로 **형상관리에서 제외 가능한지** 인프라·홈페이지 담당부서와 확인할 가치가 있습니다.
가능하다면 시행일 당일 반영이 현실적으로 가능해집니다.

### 4-4. 그 외 확인 사항

| # | 항목 | 확인처 |
|---|---|---|
| 1 | 본문 영역의 정확한 HTML 구조 (감쌀 컨테이너, 여백) | 개발팀 |
| 2 | 기존 화면에서 include 가능한지 (JSP/SSI 지원 여부) | 개발팀 |
| 3 | 펀드슈퍼마켓·IR 사이트 등 **사본 위치 전체** | 홈페이지 담당부서 |
| 4 | 모바일 앱에서 이 URL을 웹뷰로 사용할 수 있는지 | 앱 소관 부서 |
| 5 | 파일 전달 방식 (메일 / 공유 폴더 / 형상관리 PR) | 개발팀 |

> 3번은 기획안 0단계(사본 전수조사)와 동일한 항목입니다. **이 방식을 적용해도 사본이 남아 있으면 불일치는 그대로**이므로,
> 인계 방식 전환과 함께 사본 정리를 진행해야 효과가 완결됩니다.

## 5. 인계 절차

### 5-1. 표준 절차

```
1. 정보보호부   조항 수정 → 검토 → 승인
2. 정보보호부   관리 콘솔에서 파일 세트 생성
3. 정보보호부   생성 파일 자체 확인 (브라우저로 열어 육안 확인)
4. 정보보호부 → 개발팀   파일 세트 전달 (시행일 명시)
5. 개발팀       지정 경로에 파일 교체
6. 개발팀       배포
7. 정보보호부   반영 확인 (5-3 참조)
```

### 5-2. 생성 파일 규칙

각 파일 첫 부분에 다음이 자동으로 기록됩니다.

```html
<!-- 개인정보처리방침 · 본문 · 버전 v8 · 시행 2026-03-12 · 생성 2026-08-12 -->
<!-- 이 파일은 개인정보처리방침 관리 콘솔에서 생성되었습니다. 직접 편집하지 마십시오. -->
<div class="pp-doc" data-policy-version="v8" data-effective-from="2026-03-12">
```

- **직접 편집 금지.** 수정이 필요하면 콘솔에서 다시 생성합니다. 파일을 직접 고치면 다음 생성 시 덮어써집니다.
- `data-policy-version` / `data-effective-from` 속성으로 **어느 버전이 올라가 있는지 브라우저에서 즉시 확인**됩니다.

### 5-3. 반영 확인 체크리스트

| # | 확인 항목 | 방법 |
|---|---|---|
| 1 | 올바른 버전이 반영되었는가 | 페이지 소스에서 `data-policy-version` 확인 |
| 2 | 시행일이 맞는가 | 화면 상단 시행일 표기 |
| 3 | 목차 앵커가 동작하는가 | 목차 항목 클릭 |
| 4 | 표가 모바일에서 가로 스크롤되는가 | 모바일 폭에서 확인 |
| 5 | 이전본·변경내역 링크가 열리는가 | 각 링크 클릭 |
| 6 | 사본 위치가 함께 갱신되었는가 | 4-4의 3번 목록 대조 |

## 6. 이 방식의 한계 — 알고 시작해야 할 것

본 방식은 **기획안의 완성형이 아니라 실행 가능한 첫 단계**입니다. 다음은 여전히 남습니다.

| 항목 | 본 방식 | 기획안 CMS |
|---|---|---|
| 파일 생성 | 관리 콘솔 (단일 파일 도구) | 서버 시스템 |
| 승인 워크플로 | **시스템 밖 (기존 결재 절차)** | 시스템 내 결재 |
| 예약 게시 | **불가 (수동 반영)** | 시행일 자동 게시 |
| 접근 권한 통제 | **없음 (파일 도구)** | 역할별 권한 |
| 감사 로그 | **없음** | 전체 상태 전이 기록 |
| 스냅샷 해시 증빙 | **없음** | 게시 시점 해시 보관 |
| 조항 데이터 저장 | **도구 내부** | DB |

> 즉 본 방식은 **"게시 반영 구간"의 문제를 해결**하고, **"통제·증빙 구간"은 뒤로 미룹니다.**
> 현재 가장 큰 통증이 게시 반영 구간(리드타임·오탈자)이므로 우선순위 판단으로는 타당합니다.
>
> 다만 **개인정보 처리방침 평가제나 감독 대응에서 승인 이력·게시 증빙을 요구받는 경우**,
> 기획안의 CMS 단계가 필요해집니다. 그때를 대비해 본 방식의 산출물 구조를
> **CMS의 스냅샷 출력 규격과 동일하게** 설계해 두었습니다 — 이관 시 버릴 것이 없습니다.

## 7. 홈페이지 재구축과의 관계

재구축 사업이 언제 진행될지 불확실한 상황에서, 본 방식은 **어느 시점에 재구축이 오더라도 손실이 없도록** 설계되었습니다.

| 재구축 시점 | 본 방식의 상태 |
|---|---|
| 재구축 전 | 기존 프레임에서 include로 동작 |
| **재구축 중** | 파일은 그대로. 새 프레임에서 **include 한 줄만** 다시 연결 |
| 재구축 후 | 필요 시 스타일을 새 홈페이지 CSS로 통합 (4-1 방식 A로 전환) |

> **재구축 RFP에 한 줄 넣어두시면 됩니다.**
> *"개인정보처리방침 등 정책 문서는 `/static/policy/` 경로의 외부 파일을 include하는 구조를 유지할 것"*
>
> 이 한 줄이 있으면 재구축 업체가 방침을 화면에 하드코딩하는 것을 막을 수 있습니다.
> 없으면 지금과 똑같은 구조가 새 홈페이지에 그대로 재현됩니다.

## 8. 다문서 확장 — 정책 문서 허브

### 8-1. 정보보호부 소관 대고객 게시 문서

개인정보처리방침 하나만 다루는 구조로 시작하면, 나머지 문서는 여전히 수작업으로 남습니다.
정보보호부가 소관하는 대고객 게시 문서는 최소 다음과 같습니다.

| 문서 | 근거 법령 | 현재 게시 위치 |
|---|---|---|
| 개인정보처리방침 | 개인정보 보호법 제30조 | 펀드슈퍼마켓 탭 + IR 사이트 |
| **고객정보취급방침** | **금융지주회사법 제48조의2** | `www.wooriib.com/ir/main/privacy.do` |
| 신용정보 활용체제 | 신용정보의 이용 및 보호에 관한 법률 | IR 사이트 |

> **[확인 필요]** IR 사이트 푸터에 개인신용정보관리·보호인 등 정책 문서 링크가 추가로 확인됩니다.
> 소관 부서와 문서 목록을 전수 확인해 허브 대상 범위를 확정해야 합니다.

### 8-2. 핵심 — 문서마다 오너십 유형이 다르다

**이 구분을 하지 않으면 설계가 틀립니다.**

| 유형 | 문서 | 제정 주체 | 당사 역할 | 개정 트리거 | 조항 편집 |
|---|---|---|---|---|---|
| **OWN** | 개인정보처리방침, 신용정보 활용체제 | 당사 | 제정·개정·게시 | 당사 판단 | **가능** |
| **GROUP** | 고객정보취급방침 | **우리금융지주** | **게시만** | **그룹 통보** | **불가** |

고객정보취급방침은 본문 전체가 *"우리금융그룹은…"* 으로 서술되고, 제공처에 15개 그룹사가,
말미에 15개 그룹사 고객정보관리인이 나열되어 있습니다. **그룹이 제정하고 각 그룹사가 게시하는 공통 문서**입니다.

> **그룹 제공 문서를 조항 단위로 편집하면 안 됩니다.** 원문을 변형하는 것이기 때문입니다.
> 관리의 초점이 **"편집·승인"이 아니라 "수신·게시 추적"** 으로 바뀝니다.

| | OWN 문서 | GROUP 문서 |
|---|---|---|
| 관리 대상 | 조항 내용 | **원문 파일 + 게시 상태** |
| 기록할 것 | 변경 사유, 승인자, 시행일 | **그룹 시행일, 수신일, 당사 게시일, 게시 확인자** |
| 워크플로 | 작성 → 검토 → 승인 → 게시 | **수신 → 검토(대조) → 게시** |
| 변경내역 | 자동 신구대조표 | 그룹 제공 내역 전재 (있는 경우) |
| 미이행 리스크 | 개정 지연 | **그룹 개정을 당사가 게시하지 않음** |

**GROUP 문서에서 가장 큰 리스크는 "그룹이 개정했는데 당사 게시가 누락되는 것"입니다.**
현재는 이를 추적할 수단이 없습니다. 허브에 `그룹 시행일` 과 `당사 게시일` 을 나란히 두면
**두 날짜의 차이가 곧 지체 일수**로 드러나고, 누락은 미게시 상태로 즉시 보입니다.

### 8-3. 게시 의무가 문서에 명시되어 있습니다

고객정보취급방침 III-⑥ 원문입니다.

> "고객정보의 제공 및 이용 관련 취급방침의 제·개정시 **지체없이** 그 내용을 기존의 고객에게 통지하거나
> 일간지에 공고하고, 각 영업점(본점 해당부서 포함), 그리고 **각 그룹사 홈페이지 등에 게시**하는 등
> 고객공지 의무에 최선을 다할 것입니다."

**"지체없이 게시"가 문서 자체에 적혀 있습니다.** 그런데 현재 구조에서는 그룹 개정 통보를 받은 뒤
개발 요청 → 빌드 → 배포를 거쳐야 하고, 그 리드타임이 곧 "지체"입니다.

> 개인정보처리방침 제17조의 *"변경 전·후를 비교하여 공개"* 와 같은 구조의 논거입니다.
> **새 의무를 만드는 것이 아니라, 이미 문서에 적힌 의무를 지킬 수 있는 구조를 만드는 것**입니다.

### 8-4. 현행 고객정보취급방침 진단

같은 부서가 관리하는데 문서 간 관리 수준 차이가 큽니다.

| 항목 | 개인정보처리방침 | **고객정보취급방침** |
|---|---|---|
| 제정일·시행일 표기 | 3단 구분 (제정/시행/최근개정) | **없음** |
| 이전본 제공 | 7개 + 적용기간 명시 | **없음** |
| 변경내역 | 개정내역 링크 제공 | **없음** |
| 하드코딩 대상 | CPO·CCTV 담당자 | **그룹사 15개 + 고객정보관리인 15개** |

그룹사 목록은 계열사 편입·매각 시마다 바뀝니다. **개인정보처리방침의 CPO 하드코딩과 같은 문제이면서
변경 빈도는 더 높습니다.** 다만 이 목록은 그룹이 정하므로, 당사 조직 마스터가 아니라
**그룹 제공 원문의 일부**로 취급해야 합니다.

### 8-5. 허브 구조 — 모델 변경 없이 확장됩니다

기획안(`docs/02` 5-1)의 `Policy` 개체에 `code` 와 `ownership` 만 있으면 그대로 확장됩니다.

```
Policy(code="privacy-policy",     ownership=OWN)    개인정보처리방침
Policy(code="customer-info",      ownership=GROUP)  고객정보취급방침
Policy(code="credit-info-system", ownership=OWN)    신용정보 활용체제
```

버전·조항·변경내역·스냅샷·게시 이력이 전부 공통이고 `code` 와 `ownership` 만 다릅니다.
인계 파일 세트도 그대로 늘어납니다.

```
/static/policy/
  ├─ privacy-policy.html                 · -history · -changes · -diff-*
  ├─ customer-info.html                  (그룹 제공 원문)
  ├─ credit-info-system.html
  └─ policy-index.html                   ← 허브 진입 화면 (문서 목록)
```

> 토스증권이 정확히 이 구조입니다. `contents/terms?id=29`(처리방침) / `id=31`(신용정보 활용체제) /
> `id=255`(제3자 제공 현황) / `id=257`(알기쉬운 방침)이 **하나의 레지스트리**에 들어 있습니다.

### 8-6. 정본 위치와 노출 위치는 분리합니다

`www.wooriib.com` 은 IR·기업 사이트이고, 실제 거래 서비스는 `fundsupermarket.wooriib.com` 입니다.
정책 문서를 IR 사이트에만 두면 **거래 화면에서 방침을 찾는 고객이 다른 사이트로 이동**해야 합니다.
개인정보 보호법 제30조의 *"정보주체가 쉽게 확인할 수 있도록 공개"* 관점에서 불리할 수 있습니다.

```
정본   허브 1개소                        ← 파일 세트를 생성·관리하는 기준점
노출   IR 사이트 / 펀드슈퍼마켓 / 앱 / 고객센터
```

도메인이 다르면 서버 사이드 include가 까다로울 수 있습니다.
그 경우 **각 채널에 같은 파일 세트를 배포**하는 방식이 현실적입니다.
파일이 하나의 도구에서 생성되므로 **사본이 늘어도 내용은 어긋나지 않습니다** —
현재 사본 문제의 본질은 사본의 개수가 아니라 각 사본을 사람이 따로 고치는 데 있습니다.

### 8-7. 함께 하면 유리한 이유

개발팀과 협의할 항목(경로 고정, include 방식, 스타일 소유권, 형상관리 제외 여부)은
**문서 개수와 무관**합니다. 한 번 합의하면 그 뒤로는 파일이 몇 개든 같은 절차입니다.

문서별로 따로 추진하면 **같은 협의를 처음부터 반복**하게 됩니다.

## 9. 도구 — 관리 콘솔의 인계 파일 내보내기

`prototype/policy-console.html` 의 **07 인계 파일 내보내기** 화면에서 파일 세트를 생성합니다.

- 조항을 수정하면 즉시 반영된 HTML이 생성됩니다
- **파일 형태**(본문 조각 / 독립 페이지)와 **스타일 포함 여부**를 선택할 수 있습니다
- 파일별 미리보기 · 클립보드 복사 · 다운로드 지원
- 조직 마스터를 수정하면 생성 파일에도 즉시 반영됩니다 (개정 절차 없이)

이 도구는 **단일 HTML 파일이며 외부 리소스를 참조하지 않습니다.** 폐쇄망에서 그대로 동작합니다.
