## 0. 조사 범위와 한계 (먼저 읽어주세요)

이번 분석 환경에서 3사 웹사이트 도메인(`corp.tossinvest.com`, `kakaopaysec.com`, `fundsupermarket.wooriib.com`)이
네트워크 egress 정책상 **모두 차단**되어 본문 원문을 직접 수집하지 못했습니다.

따라서 본 문서의 근거는 다음으로 한정됩니다.

| 근거 유형 | 확보 여부 | 신뢰도 |
|---|---|---|
| URL / 라우팅 구조 (문서 ID, 버전 파라미터, 엔드포인트 명명) | 확보 | **높음** — 시스템 설계가 URL에 그대로 드러남 |
| **전체 페이지 캡처 이미지 (3사)** | **확보 (2026-08-12 추가)** | **높음** — 레이아웃·정보구조 판별 가능 |
| 페이지 제목 · 시행일 등 검색 메타데이터 | 부분 확보 | 중간 |
| 조항별 본문 텍스트 (전문 대조) | **미확보** | 캡처 해상도상 본문 판독 불가 |

> **본문 대조가 필요한 항목은 6장에 별도 표시**했습니다. 아래 중 하나로 보완 가능합니다.
> ① 3개 도메인을 환경 네트워크 허용목록에 추가 → 재수집
> ② 각 페이지의 HTML 또는 텍스트를 저장소에 붙여넣기 → 조항 단위 정밀 비교 수행
>
> **[확인 필요]** 제공받은 캡처 중 카카오페이증권과 우리투자증권 이미지가 레이아웃상 구분되지 않습니다.
> 동일 파일 중복 첨부인지, 실제 유사인지 확인 후 8장의 해당 부분을 분리 기술할 예정입니다.
> 현재 8장은 두 곳을 **"문서 이식형"** 으로 묶어 기술합니다.

## 1. 한 줄 결론

> 3사는 같은 문서를 만들고 있는 게 아니라, **서로 다른 세대의 시스템**으로 관리하고 있습니다.
> 토스증권 = **콘텐츠 레지스트리(3세대)**, 카카오페이증권 = **게시판형 CMS(2세대)**, 당사 = **화면 하드코딩(1세대)**.

당사의 문제는 "Word로 만들어서 불편하다"가 아니라, **게시된 결과물의 구조 자체가 버전을 표현하지 못한다**는 데 있습니다.
내부 프로세스(CMS 도입)만 개선하고 게시 구조를 그대로 두면, 개선 효과의 절반이 사라집니다.

## 2. 3사 게시 아키텍처

### 2-1. 토스증권 — 콘텐츠 레지스트리형

관찰된 URL 패턴:

```
https://corp.tossinvest.com/ko/contents/terms?id=29         ← 개인정보 처리방침 (문서 ID 고정)
https://corp.tossinvest.com/en/terms/v2?id=29               ← 동일 문서, 다국어 + 신규 렌더러
https://corp.tossinvest.com/contents/consent/?id=111&version=191
https://corp.tossinvest.com/ko/contents/consent/preview?id=303&version=818
https://corp.tossinvest.com/ko/contents/terms?id=257         ← "알기쉬운 개인정보 처리방침" (별도 문서)
https://corp.tossinvest.com/ko/contents/terms?id=255         ← 개인(신용)정보 제3자 제공 현황
https://corp.tossinvest.com/ko/contents/terms?id=31          ← 신용정보 활용체제
https://service.toss.im/terms/2947                           ← 개인정보 처리방침(구버전) 영구 링크
```

여기서 읽어낼 수 있는 설계:

1. **`id` = 문서(Document), `version` = 버전(Version)으로 분리**되어 있습니다.
   문서 ID는 개정과 무관하게 고정되고, 버전은 별도 식별자를 가집니다. → 교과서적인 2계층 콘텐츠 모델.
2. **버전이 URL로 주소지정(addressable)됩니다.** `?id=111&version=191` 형태로 특정 시점 문서를 영구 링크로 인용할 수 있습니다.
3. **`preview` 엔드포인트가 존재**합니다 → 게시 전 검토(초안 미리보기) 기능이 시스템에 내장되어 있음을 시사합니다. 승인 워크플로가 있다는 강한 정황.
4. **`/ko/`, `/en/` 경로 분리 + 동일 `id`** → 하나의 문서에 언어별 번역본이 매달린 i18n 구조.
5. **`contents/terms` 와 `terms/v2` 가 공존** → 콘텐츠 저장소는 그대로 두고 **렌더러(표시 화면)만 교체**한 흔적. 원본과 표현이 분리되어 있다는 증거입니다.
6. **약관·처리방침·동의서·제3자 제공 현황·신용정보 활용체제가 전부 같은 레지스트리**에 들어 있습니다.
   개인정보처리방침만을 위한 시스템이 아니라, **대고객 고지사항 전체를 하나의 체계로 관리**하고 있습니다.
7. **"알기쉬운 개인정보 처리방침"이 별도 문서(id=257)로 존재**합니다. 정식본과 요약본을 함께 게시.

### 2-2. 카카오페이증권 — 게시판(Board)형 CMS

관찰된 URL 패턴:

```
https://kakaopaysec.com/caution/privacyCaution/dynamicBoardPageLatest.do?code=privacy-policy
https://kakaopaysec.com/caution/privacyCaution/dynamicBoardPageDetail.do?id=7256
https://www.kakaopaysec.com/caution/privacyCaution/dynamicBoardPageDetail.do?id=5228
https://kakaopaysec.com/caution/privacyCaution/dynamicBoardPageDetail.do?id=6677
```

설계 해석:

1. **`dynamicBoard` = 범용 동적 게시판 CMS**입니다. 개인정보처리방침 전용 시스템이 아니라, 공용 CMS의 한 게시판을 쓰고 있습니다.
2. **`Latest.do?code=privacy-policy`** — 논리적 코드로 "현재 유효본"을 해석해주는 엔드포인트가 있습니다.
   → 고정 URL(`code=privacy-policy`)은 그대로 두고, 내부에서 최신 게시글을 가리키는 **포인터 구조**. 좋은 패턴입니다.
3. **`Detail.do?id=7256 / 6677 / 5228`** — 개정본마다 게시글 ID가 새로 발번됩니다.
   → 과거 버전이 삭제되지 않고 **각각 영구 URL을 가진 채 보존**됩니다.
4. 다만 이는 **버전 모델이 아니라 게시글 모델**입니다. 즉 "v1.2"라는 개념이 아니라 "7256번 글"이며,
   문서(Document)와 버전(Version)의 부모-자식 관계가 데이터에 명시되어 있지 않을 가능성이 높습니다.
5. `.do` 확장자 = Spring MVC 계열 레거시 스택. **기술은 낡았지만 운영 모델은 이미 콘텐츠 기반**입니다.
   → 즉, 최신 기술 없이도 목표 상태에 도달할 수 있다는 뜻이기도 합니다.

### 2-3. 우리투자증권(당사) — 화면 하드코딩형

관찰된 URL 패턴:

```
https://fundsupermarket.wooriib.com/fmc/FMC5010001/main.do?tabNum=3   ← "약관 및 유의사항" 화면의 3번 탭
https://www.wooriib.com/ir/main/privacy2.do                            ← 별도 도메인의 개인정보처리방침
https://www.wooriib.com/ir/main/privacy3.do                            ← 같은 경로의 또 다른 방침 페이지
```

설계 해석 — **여기가 핵심 진단입니다.**

1. **문서 식별자가 없습니다.** `FMC5010001`은 개인정보처리방침의 ID가 아니라 **화면(Screen) ID**입니다.
   개인정보처리방침은 "약관 및 유의사항"이라는 화면 안의 **세 번째 탭**이라는 위치로만 식별됩니다.
   → 콘텐츠가 독립 개체가 아니라 **화면의 부속물**입니다.
2. **버전이 URL에 존재하지 않습니다.** `tabNum=3`은 버전이 아니라 탭 번호입니다.
   → 특정 시점의 방침을 링크로 지목할 수 없습니다. 분쟁·민원·감독기관 대응 시 "당시 게시본"을 증빙하기 어렵습니다.
3. **버전이 파일명으로 표현되고 있습니다.** `privacy2.do`, `privacy3.do` 형태는
   개정 시 **페이지 파일을 하나 더 만드는 방식**의 전형적 흔적입니다.
   → 개정할수록 소스가 증식하고, 각 페이지의 유효기간(시행일~종료일) 메타데이터는 어디에도 없습니다.
4. **동일 콘텐츠가 최소 2개 도메인에 각각 존재**합니다 (`www.wooriib.com` / `fundsupermarket.wooriib.com`).
   여기에 모바일 앱, PDF 보관본, 내부 원본(Word)까지 더하면 **정본(Source of Truth)이 4~5벌**입니다.
   → "어느 것이 최신인가"를 사람이 확인해야 하는 상태. 이건 편의성 문제가 아니라 **컴플라이언스 리스크**입니다.
5. **탭 UI 안에 갇혀 있어** 개인정보처리방침 자체의 고유 URL·직접 진입점이 약합니다.
   (개인정보 보호법상 요구되는 "정보주체가 쉽게 확인할 수 있도록 공개" 관점에서 불리)

## 4. 당사의 구조적 취약점 (우선순위 순)

### ① 정본(Source of Truth)이 복수로 존재 — **최우선 리스크**
도메인별 사본 + PDF 보관본 + 내부 Word 원본이 각각 존재합니다.
개정 시 한 곳이라도 누락되면 **서로 다른 방침이 동시에 대고객 게시되는 상태**가 됩니다.
개인정보 보호법 제30조의 공개 의무 관점에서 단순 실수로 넘기기 어려운 사안입니다.

### ② 버전이 데이터가 아니라 파일로 관리됨
`privacy2 / privacy3` 방식은 개정 횟수만큼 소스가 늘어납니다.
"2025년 6월 시점에 게시 중이던 방침"을 특정하려면 사람이 파일과 배포 이력을 추적해야 합니다.
→ 민원·분쟁·감독 대응 시 **입증 비용이 곧 리스크**입니다.

### ③ 과거본에 영구 링크가 없음
타사 2곳은 모두 과거본이 고유 URL로 살아 있습니다.
당사는 과거본이 PDF 파일로만 남아 있어, 인용·비교·검색이 불가능합니다.
> 참고: 개인정보 보호법 시행령상 방침 변경 시 **변경 내용을 지속 공개하고 정보주체가 변경 사항을 쉽게 알 수 있도록** 해야 합니다.
> 변경 전·후 비교 제공은 감독기관 안내서에서 권장되는 방식이며, 2024년 시행된 **개인정보 처리방침 평가제**(법 제30조의2)에서도
> 가독성·접근성·이력 공개가 평가 요소로 다뤄집니다. **정확한 최신 요건은 개인정보보호위원회 고시·안내서로 확인이 필요합니다.**

### ④ 콘텐츠 수정이 개발 배포에 종속
문구 하나 수정에 개발·빌드·배포가 필요합니다.
이는 리드타임 문제이면서 동시에 **시행일 준수 리스크**입니다(법정 시행일에 배포 창구가 닫혀 있으면 대응 불가).

### ⑤ 조항 단위 관리 불가
현재는 문서 전체가 하나의 덩어리입니다. 제7조만 바뀌어도 전체를 다시 만들고 다시 배포합니다.
변경 이력도 "문서가 바뀌었다" 수준으로만 남고, **무엇이 왜 바뀌었는지는 데이터로 남지 않습니다.**

### ⑥ 요약본·다국어 대응 여력 없음
토스증권은 정식본과 별도로 "알기쉬운 처리방침"을, 그리고 국·영문을 동일 문서 ID로 운영합니다.
현재 당사 구조에서는 요약본이나 영문본을 추가하는 순간 **관리 대상 사본이 2배로 늘어납니다.**

## 5. 개선 방향 — 타사 벤치마킹을 시스템 요구사항으로 환산

### 5-1. 데이터 모델: 문서 / 버전 / 조항 3계층

```
Policy (문서)                      code = "privacy-policy", 문서 ID 고정, 절대 변하지 않음
  └─ PolicyVersion (버전)          version_no, 시행일, 종료일, 상태(DRAFT/REVIEW/APPROVED/SCHEDULED/ACTIVE/ARCHIVED)
       └─ Section (조항 블록)      section_key(UUID·불변), 표시번호(자동 채번), 제목, 본문, 표, 링크
            └─ ChangeLog           변경유형, 변경사유, 변경자, 승인자, before/after
```

**설계 시 반드시 지킬 원칙 하나** — 조항에는 **표시 번호와 별개의 불변 키(`section_key`)를 부여**해야 합니다.
조항이 신설·삭제되면 "제7조"가 "제8조"로 밀립니다. 번호를 키로 쓰면 그 순간 **변경 이력과 Diff가 전부 깨집니다.**
표시 번호는 렌더링 시점에 자동 채번하고, 이력 추적은 불변 키로 합니다. (첨부해주신 CMS 구상에서 보완이 필요한 지점입니다.)

### 5-2. URL 규약: 버전을 주소로 노출

타사 2곳이 이미 하고 있고, 당사만 없는 기능입니다. 시스템 구축의 **필수 산출물**로 잡아야 합니다.

```
/privacy-policy                     ← 현재 유효본 (canonical, 영구 고정)
/privacy-policy/v/{versionId}       ← 특정 버전 영구 링크 (불변, 삭제 금지)
/privacy-policy/history             ← 시행기간 + 버전 목록
/privacy-policy/diff/{from}/{to}    ← 변경 전·후 비교표 (조항 단위 자동 생성)
/privacy-policy/summary             ← 알기쉬운 처리방침 (같은 버전의 다른 뷰)
/privacy-policy.pdf                 ← 현재본 PDF (자동 생성 산출물)
```

핵심은 **`/privacy-policy` 하나만 대외 공식 주소로 삼고, 모든 채널(홈페이지·펀드슈퍼마켓·앱·고객센터)이 이를 참조**하는 것입니다.
도메인별 사본은 신규 시스템 오픈과 동시에 **폐기하거나 리다이렉트** 처리해야 합니다. 이게 1번 리스크의 유일한 해법입니다.

### 5-3. 요약본은 별도 문서가 아니라 "같은 버전의 다른 뷰"

토스증권은 정식본(id=29)과 알기쉬운 방침(id=257)을 **별도 문서**로 운영합니다.
이 방식은 구현은 쉽지만 **두 문서의 개정 시점이 어긋날 위험**이 있습니다.
당사는 후발주자 이점을 살려, 요약본을 같은 `PolicyVersion`에 매달린 뷰로 설계해 **동시 게시를 시스템이 보장**하도록 하는 것을 권합니다.

### 5-4. 배포 방식: API 실시간 호출보다 "게시 시점 스냅샷 푸시"

첨부해주신 구상에서는 홈페이지가 CMS를 API로 실시간 호출하는 그림이었는데,
금융회사 환경에서는 **대외 홈페이지(DMZ)가 내부 CMS를 실시간 호출하는 구조는 망분리·보안심의에서 막힐 가능성**이 높습니다.
또한 CMS 장애가 곧 대고객 화면 장애가 됩니다.

권장 구조:

```
CMS(내부망)  ──[승인·게시 시점 1회 푸시]──▶  정적 스냅샷(HTML/JSON) ──▶ 홈페이지 / 펀드슈퍼마켓 / 앱 웹뷰
                                                    │
                                                    └─ 게시 스냅샷 + 해시 + 타임스탬프 보관 (감사·증빙용)
```

- 대외 화면은 **정적 파일만 읽습니다** → 가용성·보안 모두 유리
- 게시 시점 스냅샷의 **해시를 함께 보관**하면 "당시 게시본"의 무결성을 증빙할 수 있습니다 (PDF 보관보다 강력)
- 앱은 스토어 심사 없이 **웹뷰로 동일 URL을 렌더링** → 버전 불일치 원천 차단

### 5-5. 예약 게시는 "스케줄러 + 실패 알림"까지가 요건

시행일 00:00 자동 게시는 편의 기능이 아니라 **법정 시행일 준수 수단**입니다.
따라서 예약 게시 실패 시 담당자 알림, 게시 결과 검증(헬스체크), 수동 강제 게시 경로가 함께 설계되어야 합니다.

## 7. 추진 우선순위 제안

| 단계 | 내용 | 이유 |
|---|---|---|
| **0단계 (선행)** | **정본 확정 및 사본 현황 전수조사** — 현재 개인정보처리방침이 게시된 모든 위치(도메인·앱·PDF·내부문서) 목록화, 내용 일치 여부 대조 | 시스템을 만들어도 사본이 남아 있으면 불일치 리스크가 그대로 유지됨. 조사 결과가 곧 이관 범위이자 기획안의 As-Is 근거자료 |

> 참고: 1단계만 완료하면 **담당자 업무는 편해지지만 대외 게시 구조의 취약점은 그대로**입니다.

## 8. [추가] 화면 캡처 기반 분석 — "웹 네이티브 콘텐츠" vs "문서 이식"

2장~7장은 URL 구조 분석이었고, 이 장은 **실제 게시 화면 캡처**를 근거로 합니다.
그리고 여기서 **URL 분석보다 더 직접적인 격차**가 드러납니다.

### 8-1. 토스증권 — 웹 콘텐츠로 "설계된" 방침

캡처에서 확인되는 특징:

1. **문서 상단에 목차(TOC) 블록이 있습니다.** 10개 내외의 조항명이 링크로 나열되어 있고, 클릭 시 해당 위치로 이동하는 앵커 구조로 보입니다.
   → 긴 문서를 스크롤로만 탐색하지 않아도 됩니다. **정보 탐색성(Findability)** 확보.
2. **조항마다 대형 일러스트 아이콘이 배치**되어 있습니다 (모니터, 인물, 돋보기, 휴지통, 스마트폰, 문서, 사람들 등).
   → 조항 간 시각적 경계가 명확해, 원하는 조항을 눈으로 훑어 찾을 수 있습니다.
3. **표 사용이 절제되어 있습니다.** 서술형 본문이 중심이고, 표는 꼭 필요한 곳(수집항목·보유기간 등)에만 씁니다.
4. **단일 컬럼, 좁은 폭, 세로로 긴 레이아웃** = 모바일 우선 반응형. 앱 웹뷰에 그대로 얹어도 무리가 없는 형태입니다.
5. 기업 홈페이지의 GNB·브레드크럼 안에 갇혀 있지 않고, **콘텐츠가 화면의 주인공**입니다.

> 핵심: 토스증권의 방침은 **Word 문서를 웹에 옮긴 것이 아니라, 처음부터 웹 콘텐츠로 설계**된 것입니다.
> 5장에서 제안한 "문서/버전/조항 3계층 모델"이 아니면 이런 화면은 나올 수 없습니다.
> 조항이 독립 블록이어야 조항별 아이콘·앵커·개별 렌더링이 가능하기 때문입니다.
> **즉, 이 화면 자체가 조항 단위 콘텐츠 모델의 산출물이라는 방증입니다.**

### 8-2. 카카오페이증권 / 우리투자증권 — 문서를 웹에 이식한 형태

> ※ 두 캡처가 레이아웃상 구분되지 않아 우선 함께 기술합니다 (0장 [확인 필요] 참조).

캡처에서 확인되는 특징:

1. **기업 홈페이지 공통 헤더 + GNB + 브레드크럼 안에 문서가 삽입**된 형태입니다.
   개인정보처리방침이 독립 콘텐츠가 아니라 **웹사이트의 한 페이지**로 취급됩니다. (2-3장의 "화면의 부속물" 진단과 일치)
2. **목차·앵커 네비게이션이 보이지 않습니다.** 매우 긴 문서를 **스크롤로만 탐색**해야 합니다.
   → 정보주체가 "제3자 제공 항목"을 찾으려면 전체를 훑어야 합니다.
3. **표가 압도적으로 많고 복잡합니다.** 다열·병합셀 표가 페이지 상당 부분을 차지합니다.
   → 내용은 충실하지만 **가독성은 낮습니다.** 모바일에서는 가로 스크롤이 발생할 가능성이 높습니다.
4. **시각적 구분 장치가 없습니다.** 조항 제목과 본문의 크기 차이만으로 구분되어, 균일한 텍스트 덩어리로 보입니다.
5. 전형적인 **"Word 문서 → HTML 변환"** 의 결과물 형태입니다.

### 8-3. 이 차이가 왜 중요한가 — 가독성은 이제 평가 대상입니다

단순한 디자인 취향 문제가 아닙니다.

- 개인정보 보호법 제30조는 방침을 **"정보주체가 쉽게 확인할 수 있도록"** 공개할 것을 요구합니다.
- 2024년 시행된 **개인정보 처리방침 평가제(법 제30조의2)** 는 방침의 **가독성·접근성·이해 용이성**을 평가 요소로 다룹니다.
- 토스증권이 정식본과 별도로 "알기쉬운 개인정보 처리방침"(id=257)까지 운영하는 것은 이 흐름에 대한 대응으로 읽힙니다.

> **정확한 평가 대상 선정 기준과 최신 평가 항목은 개인정보보호위원회 고시·안내서로 확인이 필요합니다.**
> 다만 방향성은 명확합니다 — **"법정 기재사항을 다 넣었는가"에서 "정보주체가 실제로 이해할 수 있는가"로 기준이 이동**하고 있습니다.

현재 당사 화면은 **기재사항 충실도는 높으나 전달력이 낮은** 전형적 상태입니다.
그리고 이 문제는 담당자가 Word를 잘 쓴다고 해결되지 않습니다. **콘텐츠 모델이 조항 단위가 아니면 구조적으로 불가능**합니다.

### 8-4. 시스템 요구사항으로 추가할 항목

캡처 분석 결과, 5장 요구사항에 다음을 **추가**합니다.

| 요구사항 | 근거 | 우선순위 |
|---|---|---|
| 조항 목차 자동 생성 + 앵커 링크 | 조항이 독립 블록이면 목차는 **자동 생성 가능** (수기 관리 불필요) | 높음 |
| 조항별 아이콘/카테고리 메타데이터 | 토스 수준의 시각적 구분. 조항 스키마에 `icon`, `category` 필드 추가 | 중간 |
| 표 전용 에디터 + 반응형 렌더링 | 당사 방침은 표 비중이 매우 높음. 표를 **구조화 데이터로 저장**해야 모바일 대응·재사용 가능 | **높음** |
| 모바일 렌더링 규격 | 앱 웹뷰 공용. 표는 가로 스크롤 컨테이너로 격리 | 높음 |
| 요약본(알기쉬운 방침) 뷰 | 평가제 대응. 5-3항대로 **같은 버전의 다른 뷰**로 설계 | 중간 |
| 조항 검색 기능 | 긴 문서 탐색성 보완. 조항 단위 저장이면 자연히 확보됨 | 중간 |

특히 **표를 구조화 데이터로 저장하는 것**이 중요합니다.
표를 HTML 덩어리로 저장하면 위탁사 한 곳이 바뀔 때마다 사람이 HTML을 건드려야 하고,
3단계(고지사항 통합)에서 **위탁현황·제3자 제공 현황을 다른 문서와 공유**하는 것도 불가능해집니다.
