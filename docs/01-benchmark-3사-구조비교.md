## 0. 조사 방법과 근거

3사 개인정보처리방침 **전문(全文)을 확보**하여 조문 단위로 대조했습니다.

| 근거 유형 | 확보 방법 | 신뢰도 |
|---|---|---|
| **조문 전문 텍스트 (3사)** | 각 사 게시 페이지에서 **본문 직접 수집** | **높음** — 조문 단위 정밀 대조 수행 (9장) |
| 전체 페이지 캡처 이미지 (3사) | 게시 화면 전체 캡처 | 높음 — 레이아웃·정보구조 판별 (8장) |
| URL / 라우팅 구조 (문서 ID, 버전 파라미터, 엔드포인트 명명) | 공개 URL 및 검색 메타데이터 | 높음 — 시스템 설계가 URL에 그대로 드러남 (2장) |
| 별도 링크로 분리된 현황 문서 (위탁·제3자 제공·국외이전 상세) | **미수집** | 각 사 별도 페이지. 후속 수집 필요 |

> **분석 도구의 제약**: 분석 환경 자체는 외부 도메인 접속이 차단되어 자동 수집이 불가했고,
> 본문·캡처는 **수동으로 수집하여 반영**했습니다. 결과적으로 전문 대조에는 제약이 없습니다.
>
> 다만 3사 모두 위탁·제3자 제공 등 상세 현황은 **별도 문서로 분리**해 두었고(9-6 참조), 그 문서들은 아직 미수집입니다.
> 법령 해석이 필요한 항목은 본문에 **[확인 필요]** 로 표시했으며, 개인정보보호위원회 고시·안내서로 확인이 필요합니다.

## 1. 한 줄 결론

> 3사는 같은 문서를 만들고 있는 게 아니라, **서로 다른 세대의 시스템**으로 관리하고 있습니다.
> 토스증권 = **콘텐츠 레지스트리(3세대)**, 카카오페이증권 = **게시판형 CMS(2세대)**, 당사 = **화면 하드코딩(1세대)**.

당사의 문제는 "Word로 만들어서 불편하다"가 아니라, **게시된 결과물의 구조 자체가 버전을 표현하지 못한다**는 데 있습니다.
내부 프로세스(CMS 도입)만 개선하고 게시 구조를 그대로 두면, 개선 효과의 절반이 사라집니다.

> **조문 전문 대조(9장) 후 추가된 결론**
> 당사 방침의 **내용과 메타데이터 표기 체계는 3사 중 가장 정교합니다**(라벨링·제정일/시행일/개정일 3단 구분·이전본 적용기간 명시 — 모두 당사만 보유).
> 문제는 그 체계를 **전부 사람이 수작업으로 유지**한다는 점이며, 그 결과가 **연평균 개정 0.7회**(토스 5.7회)와
> "당행" 같은 타 업권 표현이 방침에 남아 있는 상태입니다.
> **이 과제는 부실한 문서를 고치는 일이 아니라, 잘 정의된 체계를 시스템화하는 일입니다.**

## 2. 3사 게시 아키텍처

### 2-1. 토스증권 — 콘텐츠 레지스트리형

관찰된 URL 패턴:

```
https://corp.tossinvest.com/ko/contents/terms?id=29         ← 개인정보 처리방침 (문서 ID 고정)
https://corp.tossinvest.com/en/terms/v2?id=29               ← 동일 문서, 다국어 + 신규 렌더러
https://corp.tossinvest.com/contents/consent/?id=111&version=191
https://corp.tossinvest.com/ko/contents/consent/preview?id=303&version=818
https://corp.tossinvest.com/ko/contents/terms?id=257         ← "알기쉬운 개인정보 처리방침" (별도 문서)
https://corp.tossinvest.com/ko/contents/terms?id=255         ← 개인(신용)정보 제3자 제공 현황
https://corp.tossinvest.com/ko/contents/terms?id=31          ← 신용정보 활용체제
https://service.toss.im/terms/2947                           ← 개인정보 처리방침(구버전) 영구 링크
```

여기서 읽어낼 수 있는 설계:

1. **`id` = 문서(Document), `version` = 버전(Version)으로 분리**되어 있습니다.
   문서 ID는 개정과 무관하게 고정되고, 버전은 별도 식별자를 가집니다. → 교과서적인 2계층 콘텐츠 모델.
2. **버전이 URL로 주소지정(addressable)됩니다.** `?id=111&version=191` 형태로 특정 시점 문서를 영구 링크로 인용할 수 있습니다.
3. **`preview` 엔드포인트가 존재**합니다 → 게시 전 검토(초안 미리보기) 기능이 시스템에 내장되어 있음을 시사합니다. 승인 워크플로가 있다는 강한 정황.
4. **`/ko/`, `/en/` 경로 분리 + 동일 `id`** → 하나의 문서에 언어별 번역본이 매달린 i18n 구조.
5. **`contents/terms` 와 `terms/v2` 가 공존** → 콘텐츠 저장소는 그대로 두고 **렌더러(표시 화면)만 교체**한 흔적. 원본과 표현이 분리되어 있다는 증거입니다.
6. **약관·처리방침·동의서·제3자 제공 현황·신용정보 활용체제가 전부 같은 레지스트리**에 들어 있습니다.
   개인정보처리방침만을 위한 시스템이 아니라, **대고객 고지사항 전체를 하나의 체계로 관리**하고 있습니다.
7. **"알기쉬운 개인정보 처리방침"이 별도 문서(id=257)로 존재**합니다. 정식본과 요약본을 함께 게시.

### 2-2. 카카오페이증권 — 게시판(Board)형 CMS

관찰된 URL 패턴:

```
https://kakaopaysec.com/caution/privacyCaution/dynamicBoardPageLatest.do?code=privacy-policy
https://kakaopaysec.com/caution/privacyCaution/dynamicBoardPageDetail.do?id=7256
https://www.kakaopaysec.com/caution/privacyCaution/dynamicBoardPageDetail.do?id=5228
https://kakaopaysec.com/caution/privacyCaution/dynamicBoardPageDetail.do?id=6677
```

설계 해석:

1. **`dynamicBoard` = 범용 동적 게시판 CMS**입니다. 개인정보처리방침 전용 시스템이 아니라, 공용 CMS의 한 게시판을 쓰고 있습니다.
2. **`Latest.do?code=privacy-policy`** — 논리적 코드로 "현재 유효본"을 해석해주는 엔드포인트가 있습니다.
   → 고정 URL(`code=privacy-policy`)은 그대로 두고, 내부에서 최신 게시글을 가리키는 **포인터 구조**. 좋은 패턴입니다.
3. **`Detail.do?id=7256 / 6677 / 5228`** — 개정본마다 게시글 ID가 새로 발번됩니다.
   → 과거 버전이 삭제되지 않고 **각각 영구 URL을 가진 채 보존**됩니다.
4. 다만 이는 **버전 모델이 아니라 게시글 모델**입니다. 즉 "v1.2"라는 개념이 아니라 "7256번 글"이며,
   문서(Document)와 버전(Version)의 부모-자식 관계가 데이터에 명시되어 있지 않을 가능성이 높습니다.
5. `.do` 확장자 = Spring MVC 계열 레거시 스택. **기술은 낡았지만 운영 모델은 이미 콘텐츠 기반**입니다.
   → 즉, 최신 기술 없이도 목표 상태에 도달할 수 있다는 뜻이기도 합니다.

### 2-3. 우리투자증권(당사) — 화면 하드코딩형

관찰된 URL 패턴:

```
https://fundsupermarket.wooriib.com/fmc/FMC5010001/main.do?tabNum=3   ← "약관 및 유의사항" 화면의 3번 탭
https://www.wooriib.com/ir/main/privacy2.do                            ← 별도 도메인의 개인정보처리방침
https://www.wooriib.com/ir/main/privacy3.do                            ← 같은 경로의 또 다른 방침 페이지
```

설계 해석 — **여기가 핵심 진단입니다.**

1. **문서 식별자가 없습니다.** `FMC5010001`은 개인정보처리방침의 ID가 아니라 **화면(Screen) ID**입니다.
   개인정보처리방침은 "약관 및 유의사항"이라는 화면 안의 **세 번째 탭**이라는 위치로만 식별됩니다.
   → 콘텐츠가 독립 개체가 아니라 **화면의 부속물**입니다.
2. **버전이 URL에 존재하지 않습니다.** `tabNum=3`은 버전이 아니라 탭 번호입니다.
   → 특정 시점의 방침을 링크로 지목할 수 없습니다. 분쟁·민원·감독기관 대응 시 "당시 게시본"을 증빙하기 어렵습니다.
3. **`privacy*.do` 계열의 페이지가 복수 존재합니다.**

   > **[2026-08-12 정정 — 확정]** 초기 분석에서 `privacy2.do`, `privacy3.do`를 "개정 시 페이지 파일을 하나 더 만드는 흔적"으로
   > 추정했으나 **틀렸습니다.** 실제 접속 확인 결과는 다음과 같습니다.
   >
   > | URL | 실제 문서 |
   > |---|---|
   > | `privacy.do` | **고객정보취급방침** (금융지주회사법 제48조의2) |
   > | `privacy2.do` | **개인정보처리방침**으로 리다이렉트 |
   > | `privacy3.do` | **신용정보활용체제**로 리다이렉트 |
   >
   > 즉 버전 파일이 아니라 **서로 다른 세 문서의 별칭(alias)** 입니다.

   이 확인으로 진단이 오히려 유리한 쪽으로 바뀝니다.
   **당사는 이미 정책 문서를 문서별로 분리해 게시하고 있습니다.** 즉 정책 문서 허브의 원형이 이미 존재합니다.

   남은 문제는 **식별 체계**입니다. `privacy` / `privacy2` / `privacy3` 라는 이름은 문서의 정체를 전혀 표현하지 못하고,
   문서가 늘어나면 `privacy4`, `privacy5`로 증식합니다. 각 페이지의 유효기간(시행일~종료일) 메타데이터도 없습니다.
   → 개선 방향은 "허브를 새로 만드는 것"이 아니라 **"이미 있는 것에 의미 있는 주소와 메타데이터를 부여하는 것"** 입니다.
4. **동일 콘텐츠가 최소 2개 도메인에 각각 존재**합니다 (`www.wooriib.com` / `fundsupermarket.wooriib.com`).
   여기에 모바일 앱, PDF 보관본, 내부 원본(Word)까지 더하면 **정본(Source of Truth)이 4~5벌**입니다.
   → "어느 것이 최신인가"를 사람이 확인해야 하는 상태. 이건 편의성 문제가 아니라 **컴플라이언스 리스크**입니다.
5. **탭 UI 안에 갇혀 있어** 개인정보처리방침 자체의 고유 URL·직접 진입점이 약합니다.
   (개인정보 보호법상 요구되는 "정보주체가 쉽게 확인할 수 있도록 공개" 관점에서 불리)

## 4. 당사의 구조적 취약점 (우선순위 순)

### ① 정본(Source of Truth)이 복수로 존재 — **최우선 리스크**
도메인별 사본 + PDF 보관본 + 내부 Word 원본이 각각 존재합니다.
개정 시 한 곳이라도 누락되면 **서로 다른 방침이 동시에 대고객 게시되는 상태**가 됩니다.
개인정보 보호법 제30조의 공개 의무 관점에서 단순 실수로 넘기기 어려운 사안입니다.

### ② 버전이 데이터가 아니라 파일로 관리됨
`privacy2 / privacy3` 방식은 개정 횟수만큼 소스가 늘어납니다.
"2025년 6월 시점에 게시 중이던 방침"을 특정하려면 사람이 파일과 배포 이력을 추적해야 합니다.
→ 민원·분쟁·감독 대응 시 **입증 비용이 곧 리스크**입니다.

### ③ 과거본에 영구 링크가 없음
타사 2곳은 모두 과거본이 고유 URL로 살아 있습니다.
당사는 과거본이 PDF 파일로만 남아 있어, 인용·비교·검색이 불가능합니다.
> 참고: 개인정보 보호법 시행령상 방침 변경 시 **변경 내용을 지속 공개하고 정보주체가 변경 사항을 쉽게 알 수 있도록** 해야 합니다.
> 변경 전·후 비교 제공은 감독기관 안내서에서 권장되는 방식이며, 2024년 시행된 **개인정보 처리방침 평가제**(법 제30조의2)에서도
> 가독성·접근성·이력 공개가 평가 요소로 다뤄집니다. **정확한 최신 요건은 개인정보보호위원회 고시·안내서로 확인이 필요합니다.**

### ④ 콘텐츠 수정이 개발 배포에 종속
문구 하나 수정에 개발·빌드·배포가 필요합니다.
이는 리드타임 문제이면서 동시에 **시행일 준수 리스크**입니다(법정 시행일에 배포 창구가 닫혀 있으면 대응 불가).

### ⑤ 조항 단위 관리 불가
현재는 문서 전체가 하나의 덩어리입니다. 제7조만 바뀌어도 전체를 다시 만들고 다시 배포합니다.
변경 이력도 "문서가 바뀌었다" 수준으로만 남고, **무엇이 왜 바뀌었는지는 데이터로 남지 않습니다.**

### ⑥ 요약본·다국어 대응 여력 없음
토스증권은 정식본과 별도로 "알기쉬운 처리방침"을, 그리고 국·영문을 동일 문서 ID로 운영합니다.
현재 당사 구조에서는 요약본이나 영문본을 추가하는 순간 **관리 대상 사본이 2배로 늘어납니다.**

### ⑦ 변경내역(신구비교표)이 수기로 작성됨
당사는 개정 시 **신구비교표를 사람이 직접 작성**하여 관리하고 있습니다. 여기서 두 가지 문제가 파생됩니다.

1. **누락이 구조적으로 가능합니다.** 사람이 만드는 비교표는 "바뀐 것을 기억해서 적는" 방식입니다.
   조항이 많고 표가 복잡할수록 누락 확률이 올라가며, 누락되었는지 검증할 방법도 없습니다.
   조항 단위로 저장되어 있으면 비교표는 **계산 결과**이므로 누락이 원리적으로 불가능합니다.
2. **정보주체가 직관적으로 확인하기 어렵습니다.** 별도 문서를 열어 전체를 훑어야 하고,
   "이번 개정에서 나에게 영향 있는 항목이 무엇인지"가 한눈에 들어오지 않습니다.

당사 제17조는 **"변경 전·후를 비교하여 공개합니다"라고 이미 명문화**하고 있습니다.
즉 **선언은 되어 있고 이행 수단이 수작업**인 상태이며, 이 과제의 직접적 대상입니다. 상세 비교는 9-7 참조.

## 5. 개선 방향 — 타사 벤치마킹을 시스템 요구사항으로 환산

### 5-1. 데이터 모델: 문서 / 버전 / 조항 3계층

```
Policy (문서)                      code = "privacy-policy", 문서 ID 고정, 절대 변하지 않음
  └─ PolicyVersion (버전)          version_no, 시행일, 종료일, 상태(DRAFT/REVIEW/APPROVED/SCHEDULED/ACTIVE/ARCHIVED)
       └─ Section (조항 블록)      section_key(UUID·불변), 표시번호(자동 채번), 제목, 본문, 표, 링크
            └─ ChangeLog           변경유형, 변경사유, 변경자, 승인자, before/after
```

**설계 시 반드시 지킬 원칙 하나** — 조항에는 **표시 번호와 별개의 불변 키(`section_key`)를 부여**해야 합니다.
조항이 신설·삭제되면 "제7조"가 "제8조"로 밀립니다. 번호를 키로 쓰면 그 순간 **변경 이력과 Diff가 전부 깨집니다.**
표시 번호는 렌더링 시점에 자동 채번하고, 이력 추적은 불변 키로 합니다. (첨부해주신 CMS 구상에서 보완이 필요한 지점입니다.)

### 5-2. URL 규약: 버전을 주소로 노출

타사 2곳이 이미 하고 있고, 당사만 없는 기능입니다. 시스템 구축의 **필수 산출물**로 잡아야 합니다.

```
/privacy-policy                     ← 현재 유효본 (canonical, 영구 고정)
/privacy-policy/v/{versionId}       ← 특정 버전 영구 링크 (불변, 삭제 금지)
/privacy-policy/history             ← 시행기간 + 버전 목록
/privacy-policy/diff/{from}/{to}    ← 변경 전·후 비교표 (조항 단위 자동 생성)
/privacy-policy/summary             ← 알기쉬운 처리방침 (같은 버전의 다른 뷰)
/privacy-policy.pdf                 ← 현재본 PDF (자동 생성 산출물)
```

핵심은 **`/privacy-policy` 하나만 대외 공식 주소로 삼고, 모든 채널(홈페이지·펀드슈퍼마켓·앱·고객센터)이 이를 참조**하는 것입니다.
도메인별 사본은 신규 시스템 오픈과 동시에 **폐기하거나 리다이렉트** 처리해야 합니다. 이게 1번 리스크의 유일한 해법입니다.

### 5-3. 요약본은 별도 문서가 아니라 "같은 버전의 다른 뷰"

토스증권은 정식본(id=29)과 알기쉬운 방침(id=257)을 **별도 문서**로 운영합니다.
이 방식은 구현은 쉽지만 **두 문서의 개정 시점이 어긋날 위험**이 있습니다.
당사는 후발주자 이점을 살려, 요약본을 같은 `PolicyVersion`에 매달린 뷰로 설계해 **동시 게시를 시스템이 보장**하도록 하는 것을 권합니다.

### 5-4. 배포 방식: API 실시간 호출보다 "게시 시점 스냅샷 푸시"

첨부해주신 구상에서는 홈페이지가 CMS를 API로 실시간 호출하는 그림이었는데,
금융회사 환경에서는 **대외 홈페이지(DMZ)가 내부 CMS를 실시간 호출하는 구조는 망분리·보안심의에서 막힐 가능성**이 높습니다.
또한 CMS 장애가 곧 대고객 화면 장애가 됩니다.

권장 구조:

```
CMS(내부망)  ──[승인·게시 시점 1회 푸시]──▶  정적 스냅샷(HTML/JSON) ──▶ 홈페이지 / 펀드슈퍼마켓 / 앱 웹뷰
                                                    │
                                                    └─ 게시 스냅샷 + 해시 + 타임스탬프 보관 (감사·증빙용)
```

- 대외 화면은 **정적 파일만 읽습니다** → 가용성·보안 모두 유리
- 게시 시점 스냅샷의 **해시를 함께 보관**하면 "당시 게시본"의 무결성을 증빙할 수 있습니다 (PDF 보관보다 강력)
- 앱은 스토어 심사 없이 **웹뷰로 동일 URL을 렌더링** → 버전 불일치 원천 차단

### 5-5. 예약 게시는 "스케줄러 + 실패 알림"까지가 요건

시행일 00:00 자동 게시는 편의 기능이 아니라 **법정 시행일 준수 수단**입니다.
따라서 예약 게시 실패 시 담당자 알림, 게시 결과 검증(헬스체크), 수동 강제 게시 경로가 함께 설계되어야 합니다.

## 7. 추진 우선순위 제안

첨부해주신 3단계 안(문서관리 개선 → 홈페이지/앱 연계 → 고지사항 통합)에 **0단계를 추가**할 것을 권합니다.

| 단계 | 내용 | 이유 |
|---|---|---|
| **0단계 (선행)** | **정본 확정 및 사본 현황 전수조사** — 현재 개인정보처리방침이 게시된 모든 위치(도메인·앱·PDF·내부문서) 목록화, 내용 일치 여부 대조 | 시스템을 만들어도 사본이 남아 있으면 불일치 리스크가 그대로 유지됨. 조사 결과가 곧 이관 범위이자 기획안의 As-Is 근거자료 |
| 1단계 | CMS 구축 (조항 단위 편집 · 버전 · 승인 워크플로 · Audit Log · PDF 자동 생성) | 내부 업무 효율 |
| 2단계 | 채널 연계 (스냅샷 배포, 버전 영구 URL, 이력·Diff 대고객 공개, 예약 게시) | **대외 리스크 해소 — 실질적 효과는 여기서 발생** |
| 3단계 | 고지사항 통합 (동의서·위탁현황·제3자 제공 현황·신용정보 활용체제) | 토스증권 수준. 구조화 데이터 기반 자동 생성 |

> 참고: 1단계만 완료하면 **담당자 업무는 편해지지만 대외 게시 구조의 취약점은 그대로**입니다.
> 사내 보고 시 "업무 효율화"보다 **"대고객 게시 정본 일원화 및 개정 이력 증빙체계 확보"**를 상위 목표로 두는 편이 설득력이 높습니다.

## 8. [추가] 화면 캡처 기반 분석 — "웹 네이티브 콘텐츠" vs "문서 이식"

2장~7장은 URL 구조 분석이었고, 이 장은 **실제 게시 화면 캡처**를 근거로 합니다.
그리고 여기서 **URL 분석보다 더 직접적인 격차**가 드러납니다.

### 8-1. 토스증권 — 웹 콘텐츠로 "설계된" 방침

캡처에서 확인되는 특징:

1. **문서 상단에 목차(TOC) 블록이 있습니다.** 10개 내외의 조항명이 링크로 나열되어 있고, 클릭 시 해당 위치로 이동하는 앵커 구조로 보입니다.
   → 긴 문서를 스크롤로만 탐색하지 않아도 됩니다. **정보 탐색성(Findability)** 확보.
2. **조항마다 대형 일러스트 아이콘이 배치**되어 있습니다 (모니터, 인물, 돋보기, 휴지통, 스마트폰, 문서, 사람들 등).
   → 조항 간 시각적 경계가 명확해, 원하는 조항을 눈으로 훑어 찾을 수 있습니다.
3. **표 사용이 절제되어 있습니다.** 서술형 본문이 중심이고, 표는 꼭 필요한 곳(수집항목·보유기간 등)에만 씁니다.
4. **단일 컬럼, 좁은 폭, 세로로 긴 레이아웃** = 모바일 우선 반응형. 앱 웹뷰에 그대로 얹어도 무리가 없는 형태입니다.
5. 기업 홈페이지의 GNB·브레드크럼 안에 갇혀 있지 않고, **콘텐츠가 화면의 주인공**입니다.

> 핵심: 토스증권의 방침은 **Word 문서를 웹에 옮긴 것이 아니라, 처음부터 웹 콘텐츠로 설계**된 것입니다.
> 5장에서 제안한 "문서/버전/조항 3계층 모델"이 아니면 이런 화면은 나올 수 없습니다.
> 조항이 독립 블록이어야 조항별 아이콘·앵커·개별 렌더링이 가능하기 때문입니다.
> **즉, 이 화면 자체가 조항 단위 콘텐츠 모델의 산출물이라는 방증입니다.**

### 8-2. 카카오페이증권 / 우리투자증권 — 문서를 웹에 이식한 형태

두 곳은 서로 다른 시스템(카카오페이증권 = 게시판형 CMS, 당사 = 화면 하드코딩)을 쓰고 있음에도
**화면 유형은 같은 계열**로 나타납니다. 아래는 두 곳에 공통된 특징입니다.

> **여기서 카카오페이증권이 중요한 반례입니다.** 시스템은 이미 CMS 기반인데 화면은 당사와 같은 문서 이식형입니다.
> 즉 **CMS를 도입한다고 가독성이 자동으로 좋아지지 않습니다.** 콘텐츠를 조항 단위로 쪼개고 구조화하지 않으면
> CMS에 통짜 HTML 한 덩어리를 넣는 것으로 끝납니다. 과제명을 "CMS 도입"이 아니라 **"콘텐츠 구조화"** 로 잡아야 하는 근거입니다.

캡처에서 확인되는 특징:

1. **기업 홈페이지 공통 헤더 + GNB + 브레드크럼 안에 문서가 삽입**된 형태입니다.
   개인정보처리방침이 독립 콘텐츠가 아니라 **웹사이트의 한 페이지**로 취급됩니다. (2-3장의 "화면의 부속물" 진단과 일치)
2. **목차·앵커 네비게이션이 보이지 않습니다.** 매우 긴 문서를 **스크롤로만 탐색**해야 합니다.
   → 정보주체가 "제3자 제공 항목"을 찾으려면 전체를 훑어야 합니다.
3. **표가 압도적으로 많고 복잡합니다.** 다열·병합셀 표가 페이지 상당 부분을 차지합니다.
   → 내용은 충실하지만 **가독성은 낮습니다.** 모바일에서는 가로 스크롤이 발생할 가능성이 높습니다.
4. **시각적 구분 장치가 없습니다.** 조항 제목과 본문의 크기 차이만으로 구분되어, 균일한 텍스트 덩어리로 보입니다.
5. 전형적인 **"Word 문서 → HTML 변환"** 의 결과물 형태입니다.

### 8-3. 이 차이가 왜 중요한가 — 가독성은 이제 평가 대상입니다

단순한 디자인 취향 문제가 아닙니다.

- 개인정보 보호법 제30조는 방침을 **"정보주체가 쉽게 확인할 수 있도록"** 공개할 것을 요구합니다.
- 2024년 시행된 **개인정보 처리방침 평가제(법 제30조의2)** 는 방침의 **가독성·접근성·이해 용이성**을 평가 요소로 다룹니다.
- 토스증권이 정식본과 별도로 "알기쉬운 개인정보 처리방침"(id=257)까지 운영하는 것은 이 흐름에 대한 대응으로 읽힙니다.

> **정확한 평가 대상 선정 기준과 최신 평가 항목은 개인정보보호위원회 고시·안내서로 확인이 필요합니다.**
> 다만 방향성은 명확합니다 — **"법정 기재사항을 다 넣었는가"에서 "정보주체가 실제로 이해할 수 있는가"로 기준이 이동**하고 있습니다.

현재 당사 화면은 **기재사항 충실도는 높으나 전달력이 낮은** 전형적 상태입니다.
그리고 이 문제는 담당자가 Word를 잘 쓴다고 해결되지 않습니다. **콘텐츠 모델이 조항 단위가 아니면 구조적으로 불가능**합니다.

### 8-4. 시스템 요구사항으로 추가할 항목

캡처 분석 결과, 5장 요구사항에 다음을 **추가**합니다.

| 요구사항 | 근거 | 우선순위 |
|---|---|---|
| 조항 목차 자동 생성 + 앵커 링크 | 조항이 독립 블록이면 목차는 **자동 생성 가능** (수기 관리 불필요) | 높음 |
| 조항별 아이콘/카테고리 메타데이터 | 토스 수준의 시각적 구분. 조항 스키마에 `icon`, `category` 필드 추가 | 중간 |
| 표 전용 에디터 + 반응형 렌더링 | 당사 방침은 표 비중이 매우 높음. 표를 **구조화 데이터로 저장**해야 모바일 대응·재사용 가능 | **높음** |
| 모바일 렌더링 규격 | 앱 웹뷰 공용. 표는 가로 스크롤 컨테이너로 격리 | 높음 |
| 요약본(알기쉬운 방침) 뷰 | 평가제 대응. 5-3항대로 **같은 버전의 다른 뷰**로 설계 | 중간 |
| 조항 검색 기능 | 긴 문서 탐색성 보완. 조항 단위 저장이면 자연히 확보됨 | 중간 |

특히 **표를 구조화 데이터로 저장하는 것**이 중요합니다.
표를 HTML 덩어리로 저장하면 위탁사 한 곳이 바뀔 때마다 사람이 HTML을 건드려야 하고,
3단계(고지사항 통합)에서 **위탁현황·제3자 제공 현황을 다른 문서와 공유**하는 것도 불가능해집니다.

### 9-2. 당사에 없는 조항 — 신설 검토 대상

#### ① 가명정보 처리에 관한 사항 — **가장 명확한 갭**

당사 제1조(처리 목적)에 다음 문구가 있습니다.

> "개인정보보호법 제28조의2에 의해 통계작성(상업적 목적 포함), 과학적 연구(산업적 연구 포함), 공익적 기록보존 등을 위하여 **개인정보를 가명처리하여 활용할 수 있음**"

또한 제4조 보유기간 표에도 "통계작성, 과학적 연구, 공익적 기록보존 목적의 가명처리 정보" 항목이 있습니다.
**즉 가명처리를 한다고 두 곳에서 밝혔으나, 가명정보 처리에 관한 별도 조항이 없습니다.**

토스증권 제13조는 다음 6개 항목으로 구조화되어 있습니다 — 신설 시 그대로 참고 가능합니다.

```
1. 가명정보 처리 목적
2. 가명정보 처리 항목
3. 가명정보 처리 및 보유기간
4. 가명정보 제3자 제공에 관한 사항
5. 가명정보 처리의 위탁에 관한 사항
6. 가명정보의 안전성 확보조치 (관리적·기술적·물리적)
```

> **[확인 필요]** 가명정보 처리 관련 사항의 처리방침 기재 의무 범위(법 제28조의4 및 관련 고시·작성지침)는
> 개인정보보호위원회 안내서로 확인이 필요합니다. 다만 **"한다고 써 놓고 상세를 밝히지 않은"** 현재 상태는
> 의무 여부와 무관하게 문서 내부 정합성 문제입니다.

#### ② 연계정보(CI) 처리에 관한 사항

당사 제2조 항목표에 **"연계정보CI"가 5회 이상** 등장합니다(금융거래 공통 필수, 채무조정용, 퇴직연금 실물이전 조회, 국외이전 항목 등).
그러나 CI에 관한 별도 조항은 없습니다. 3사 중 토스증권만 제14조로 별도 기재하고 있으며, 구성은 다음과 같습니다.

```
1. 연계정보 처리근거 (정보통신망법 제23조의5 제1항·제4항)
2. 수집·이용 목적
3. 보유 및 이용 기간
4. 제3자 제공 및 위탁
5. 침해사고 발생 시 접수 및 절차
6. 정보주체 권리 및 행사방법
7. 안전성 확보조치 (정보통신망법 제23조의6, 주민등록번호와 분리 보관 등)
```

> **[확인 필요]** CI 처리 관련 처리방침 기재 요건은 정보통신망법 및 관련 고시 확인이 필요합니다.
> 토스증권 제14조는 **제2·4·9·15·16·17조를 상호 참조**하는 방식으로 작성되어, 중복 서술 없이 CI 관련 내용을 한곳에 모았습니다.
> 이 상호 참조 구조는 **조항이 독립 개체(앵커 보유)여야 성립**합니다 — 8-1의 진단을 조문 차원에서 재확인시켜 줍니다.

#### ③ 민감정보 처리

당사는 상단 라벨링에 **"민감정보"** 를 표시하고 있고, 제2조 "대여금고 거래" 항목에 **생체인식정보(지문)** 를 민감정보로 명시했습니다.
그러나 민감정보에 관한 별도 설명(처리 근거·목적·보유기간·안전조치)은 항목표 한 줄 외에는 없습니다.
토스·카카오페이는 민감정보 처리 자체가 없어 비교 대상이 아니며, **당사 고유의 보완 필요 지점**입니다.

### 9-3. 당사가 3사 중 가장 앞서는 점 — 유지·확대할 자산

**이 절이 중요합니다.** 당사 방침의 문제는 "내용이 부실하다"가 아닙니다.
오히려 **메타데이터 표기 체계는 3사 중 가장 정교합니다.** 문제는 그것을 전부 사람이 손으로 관리한다는 점입니다.

| 항목 | 우리투자증권 | 토스증권 | 카카오페이증권 |
|---|---|---|---|
| **주요 개인정보 표시(라벨링)** | **有** (18개 아이콘) | 無 | 無 |
| **날짜 표기 체계** | **제정일 / 시행일 / 최근 개정일 3단 구분** | 개정일만 | 제정일 + 개정일 |
| **이전 방침 적용기간** | **시작~종료 명시**<br>(2025.08.22.~2026.03.11. 적용) | 시작일만 나열 | 개정일만 |
| **변경 전·후 비교 공개 명시** | **제17조에 명문화** | 링크만 | 링크 + 신구대조표 PDF |

특히 다음 세 가지는 **그대로 데이터 모델로 옮기면 되는 수준으로 잘 정의**되어 있습니다.

1. **라벨링(18종)** — 3사 중 유일. 개인정보보호위원회 권고에 부합합니다.
   → 시스템에서는 각 조항에 `label` 메타데이터를 부여하면 **라벨 클릭 → 해당 조 이동**이 자동으로 구현됩니다.
2. **제정일 / 시행일 / 최근 개정일 3단 구분** — 5-1의 `PolicyVersion` 스키마와 정확히 일치합니다.
3. **이전 방침의 적용기간(from~to) 명시** — 3사 중 유일. 5-1의 `시행일 / 종료일` 필드가 이미 업무상 관리되고 있다는 뜻입니다.

> **보고 시 메시지**: 이 과제는 "부실한 방침을 고치는 일"이 아니라
> **"이미 잘 정의되어 있으나 수작업으로 유지되는 체계를 시스템화하는 일"** 입니다.
> 담당 부서의 기존 업무 품질을 인정하는 프레이밍이 되므로, 사내 설득에도 유리합니다.

### 9-5. 개정 빈도 격차 — 이 과제의 가장 강력한 정량 논거

각 사가 공개한 개정 이력을 집계했습니다.

| | 토스증권 | 카카오페이증권 | **우리투자증권** |
|---|---|---|---|
| 제정일 | (미표기, 이력은 2021-01-18부터) | 2020-01-07 | 2014-02-27 |
| 최근 개정일 | 2026-08-11 | 2026-05-29 | **2026-03-12** |
| 공개된 버전 수 | **32개** | 14개 (V.1~V.14) | 8개 |
| 연평균 개정 횟수 | **약 5.7회** | 약 2.2회 | **약 0.7회** |
| **2026년 개정 횟수** | **10회** | 1회 | **1회** |
| 2025년 개정 횟수 | 6회 | 1회 | 1회 |

토스증권의 2026년 개정일은 다음과 같습니다.

```
02-19, 03-26, 05-11, 05-13, 05-20, 05-21, 06-02, 06-30, 07-14, 08-11
                └────────┴────── 열흘 사이 4회 ──────┘
```

**토스증권은 5월 11일부터 21일까지 열흘 사이에 네 번 개정했습니다.**
이 빈도는 정기 개정으로는 설명되지 않습니다. 오탈자·문구·링크 수준의 수정을 **발견 즉시 반영**하고 있다는 뜻입니다.

반면 당사는 2015년~2019년 4년간, 2019년~2024년 4년 3개월간 개정 이력이 없습니다.

> **해석 시 주의**: 개정 빈도가 높은 것 자체가 우수하다는 뜻은 아닙니다.
> 그러나 **"고쳐야 할 때 고칠 수 있는가"** 는 다른 문제입니다.
> 수탁사 변경, 담당자 인사이동, 법령 개정, 오탈자 발견은 수시로 발생하는데,
> 개정 리드타임이 길면 그 기간 동안 **게시된 방침과 실제 처리 현황이 불일치**합니다.
> 이는 편의성 문제가 아니라 **개인정보 보호법 제30조의 공개 의무 이행 품질 문제**입니다.
>
> 9-4에서 발견된 "당행" 표기가 그 증거입니다.

### 9-6. 3사 공통 패턴 — 데이터 모델을 확정 짓는 발견

조문 대조에서 가장 중요한 발견입니다. **3사 모두 자주 바뀌는 표를 본문에서 분리**하고 있습니다.

| | 분리 대상 | 분리 방식 |
|---|---|---|
| 토스증권 | 제3자 제공 현황, 추가적 이용·제공 현황, 업무위탁 현황, 채용 업무 위탁 현황, 국외 이전 현황, 과거 변경 내역 | `>> 링크` 6종 |
| 카카오페이증권 | 제3자 제공, 위탁·재위탁 | `(상세 내역 보기)` 링크 |
| **우리투자증권** | 위탁 및 제휴업체 현황 | `홈페이지 >` `개인정보처리방침 >` `'…현황' 참고` **링크 3칩 → 레이어 팝업**(별도 페이지 아님, 고유 URL 없음) |

이유는 명확합니다. **수탁사 한 곳이 바뀔 때마다 방침 전체를 개정할 수는 없기 때문**입니다.

> **결론: 시스템은 "방침 본문"과 "현황 데이터"를 별도 엔티티로 분리해야 합니다.**
> 현황 데이터(위탁사·제3자 제공처·국외 이전처)는 **방침 버전과 독립적으로 갱신**되어야 하며,
> 각각 자체 기준일(as-of date)을 가져야 합니다.

```
Policy (방침 본문)                     ← 버전 관리, 개정 시 시행일 부여
   │  참조
   ▼
Registry (현황 데이터)                 ← 독립 갱신, 자체 기준일 보유
   ├─ 위탁·수탁사 현황
   ├─ 제3자 제공 현황
   ├─ 국외 이전 현황
   └─ 제휴업체 현황
```

다만 **분리 방식에서 당사만 뒤처져 있습니다.**

- 토스·카카오페이: **클릭 가능한 링크 → 별도 페이지**
- 당사: **클릭 가능한 링크는 맞으나 → 레이어 팝업(모달)**

당사 제8조 수탁업체 칸에는 `홈페이지 >` `개인정보처리방침 >` `'개인(신용)정보처리 위탁 및 제휴업체 현황' 참고`
세 개의 링크 칩이 배치되어 있고, 실제로 **클릭이 됩니다**. 다만 열리는 것이 별도 페이지가 아니라
**본문 위에 뜨는 레이어 팝업**이어서 **고유 주소가 없습니다.**

#### 팝업이라서 생기는 문제 — 텍스트 경로보다 오히려 큰 제약

| # | 제약 | 실무상 결과 |
|---|---|---|
| 1 | **고유 URL 부재** | 민원·분쟁 대응, 감독기관 제출 시 *"이 주소를 보시면 됩니다"* 라고 지목할 대상이 없음 |
| 2 | **버전을 주소로 표현 불가** | 현황 버전(g1…gN)을 각각 가리킬 수 없어 **과거 시점 현황을 지목하는 것 자체가 불가능** |
| 3 | **북마크·공유 불가** | 정보주체가 다시 찾아오려면 매번 방침 본문 → 제8조 → 링크 클릭의 3단계를 반복 |
| 4 | **검색엔진 미노출** | 「개인정보 보호법」 제26조 제2항이 요구하는 **"공개"** 의 취지에 비추어 접근성 취약 **[확인 필요]** |
| 5 | **인쇄·PDF 저장 곤란** | 팝업 내부에 별도 스크롤이 있어 전체를 한 번에 출력하기 어려움 |
| 6 | **접근성** | 모달은 포커스 트랩·ESC 닫기·스크린리더 대응이 없으면 키보드 사용자가 빠져나오기 어려움. 캡처상 팝업 내부 스크롤이 별도 존재해 모바일에서 이중 스크롤 발생 |
| 7 | **홈페이지 프레임 종속** | 팝업은 홈페이지 스크립트로 뜸. 재구축 과정에서 스크립트가 깨지면 **현황에 도달할 경로 자체가 소멸** |

> **7번이 이 프로젝트와 직결됩니다.** 요구사항 5(홈페이지 구조 비종속)와 정면으로 충돌합니다.
> 현황을 **고유 주소를 가진 독립 페이지**로 바꾸는 것이 개선의 실질입니다.
> 앞선 기술에서 이를 *"텍스트 경로 안내(링크 아님)"* 라고 적은 것은 **사실과 다릅니다.** 링크는 존재합니다.

#### 팝업 표의 실제 컬럼 — 담당부서까지 공개하고 있다

| 위탁업체명 | 위탁 목적 | 위탁하는 개인(신용)정보항목 | 담당부서 |
|---|---|---|---|
| 우리FIS | 전산인프라 토탈 아웃소싱 | 신정보시스템운영데이터 | IT기획부 |
| 이니텍 | 전자금융(인터넷뱅킹, 스마트뱅킹 등) ASP | ASP운영에 필요한 개인(신용)정보 항목 | IT기획부 |
| … | … | … | … |
| 우리은행 | 연계대출 상품 소개 및 설명 | 소개관리번호, 진행상태, 취급일, 취급금액 | 종합금융사업추진부 |

여기서 두 가지가 새로 확인됩니다.

**(1) 담당부서가 공개 항목에 포함되어 있습니다.**
IT기획부·CX기획부·리테일성장실·종합금융사업추진부·영업솔루션부 등 실제 부서명이 표에 박혀 있습니다.
**조직개편이 있으면 이 표도 손봐야 합니다.** 즉 요구사항 3(조직개편 = 데이터 수정)은 방침 본문뿐 아니라
**위·수탁 현황에도 그대로 적용**됩니다. 다만 위탁 내용이 그대로이므로 **본문 검토 대상은 아닙니다.**

**(2) 한 업체가 여러 업무를 위탁받는 경우 업체명 셀이 병합되어 있습니다.**
나이스평가정보가 `휴대폰본인확인서비스`(CX기획부)와 `연계정보(CI)발급`(IT기획부) 2건을 가지며,
위탁업체명 칸이 **rowspan으로 병합**되어 있습니다. **담당부서도 서로 다릅니다.**

> **데이터 단위는 "수탁사"가 아니라 "수탁사 × 위탁업무"입니다.**
> 수탁사를 단일 행으로 모델링하면 이 표를 재현할 수 없습니다.
> 토스증권 신구대조표의 비고 셀 병합(9-7)과 **같은 rowspan 패턴**이며, 같은 방식으로 다뤄야 합니다.
> 업체 단위 불변키(`co`)와 행 단위 불변키(`rowKey`)를 **분리**해야 사명 변경 시 해당 업체의 모든 업무 행이 함께 갱신됩니다.

또한 당사 위탁 현황 팝업에는 **기준일 표기가 없습니다.**
(토스·카카오페이 현황 문서는 미수집이므로 동일 문제 여부는 확인 필요)


#### 위탁과 제휴를 나눠 관리하는 것이 적절한가 — 결론: 나누는 것이 맞습니다

게시 팝업은 하나의 화면에 **두 개의 표**를 담고 있습니다.

| | 표1 | 표2 |
|---|---|---|
| 컬럼 | 위탁업체명 / 위탁 목적 / **위탁하는** 개인(신용)정보항목 / 담당부서 | 제휴업체명 / 제공목적 / **제공하는** 개인(신용)정보의 종류 / 담당부서 |
| 건수 | 20건 | 13건 |
| 근거 법령 | 「개인정보 보호법」 **제26조** · 「신용정보법」 제17조 | 「개인정보 보호법」 **제17조** · 「신용정보법」 제32조 |
| 성격 | 수탁자가 **위탁자의 관리·감독**을 받음 | 제3자가 **자기 목적**으로 이용 |
| 정보주체 동의 | 원칙적으로 불요 — **공개**로 갈음 | **원칙적으로 필요** |
| 사고 시 책임 | 위탁자가 사용자 책임 부담 | 제공받은 자가 독립 책임 |

**근거 법령과 요구 절차가 다르므로 분리는 옳습니다.** 오히려 하나의 표로 합치면
정보주체가 "동의한 제공"과 "동의 없이 공개로 갈음한 위탁"을 구분할 수 없게 됩니다.
컬럼 이름을 *"위탁하는"* 과 *"제공하는"* 으로 구분해 둔 것도 정확한 판단입니다.

다만 **배치와 참조 구조에는 문제가 있습니다.**

#### 문제 — 제휴가 위탁 조항에 딸려 있습니다

당사 방침의 실제 구조는 이렇습니다.

```
제6조 개인정보의 제3자 제공  ──▶  개인(신용)정보 제3자 제공 현황   (별도)
제7조 추가적인 이용·제공 판단 기준
제8조 개인정보 처리업무의 위탁 ──▶  개인(신용)정보 처리 위탁 및 제휴업체 현황  (별도)
                                     └─ 표1 위탁 20건
                                     └─ 표2 제휴 13건  ← 성격은 제3자 제공
제9조 개인정보의 국외 수집·이전 ──▶ 개인(신용)정보 국외 이전 현황  (별도)
```

**제휴는 제3자 제공인데 제8조(위탁) 쪽 현황에 들어가 있습니다.**
제6조는 별도의 "제3자 제공 현황"을 가리킵니다. 결과적으로
**같은 성격(제3자 제공)의 정보가 두 개의 현황 문서에 나뉘어** 있습니다.

> 정보주체가 *"내 정보가 어느 회사에 제공되는가"* 를 확인하려면 **두 곳을 봐야 합니다.**
> 그런데 제8조는 위탁 조항이므로, 제휴 표를 보려면 위탁 조항을 거쳐야 합니다.
> **조문과 현황의 매핑이 어긋나 있습니다.**

#### 권고 — 표는 나누되, 문서·주소·참조 조문도 함께 나눕니다

| | 지금 | 권고 |
|---|---|---|
| 표 분리 | O (유지) | **O — 그대로 유지** |
| 문서(파일) | 위탁·제휴가 한 파일 | **분리** — 하나의 표에 하나의 법적 근거 |
| 주소 | 팝업 1개, URL 없음 | **각각 고유 URL** |
| 참조 조문 | 제8조에서 둘 다 | 위탁 → **제8조**, 제휴 → **제6조**(제3자 제공)에서도 링크 |
| 제3자 제공 현황과의 관계 | 별개 문서 | 제6조에서 **제3자 제공 현황 + 제휴 현황**을 함께 안내 |

원칙은 하나입니다 — **하나의 표에 하나의 법적 근거, 하나의 조문이 자기 현황을 직접 가리킬 것.**
지금은 제8조 하나가 성격이 다른 두 표를 모두 가리키고 있습니다. **[확인 필요]** — 제휴를 제17조 제공으로 볼지,
별도 유형으로 볼지는 준법감시 확인이 필요합니다. 다만 컬럼명이 *"제공목적 / 제공하는"* 인 이상
제공으로 읽히는 것이 자연스럽습니다.

#### 두 표의 셀 병합 방향이 정반대입니다 — 데이터 모델을 결정하는 발견

| | 병합 대상 | 예 |
|---|---|---|
| **표1 (위탁)** | **업체명** 셀 | 나이스평가정보 1개 업체 : 업무 2건 (담당부서도 CX기획부 / IT기획부로 상이) |
| **표2 (제휴)** | **목적·항목·담당부서** 셀 | 펌뱅킹 1개 목적 : 신한·우리·국민은행 3개 업체 |

제휴 표에는 이런 그룹이 3개 있습니다.

- **펌뱅킹(은행계좌 연결신청)** — 신한은행 · 우리은행 · 국민은행 (자금부)
- **포트폴리오 추천 및 리밸런싱** — 디셈버앤컴퍼니자산운용 · 쿼터백자산운용 · KB자산운용 (리테일성장실)
- **투자자문서비스 및 회원관리** — 두물머리투자자문 · 플레인바닐라투자자문 · 바인투자자문 (디지털PB센터)

> **특정 컬럼을 그룹 키로 고정하면 안 됩니다.**
> 행은 **(업체 × 목적)** 튜플이고, 렌더링이 **같은 그룹 안에서 값이 같은 컬럼을 병합**해야
> 두 표가 하나의 코드로 재현됩니다. 업체 기준으로 묶으면 표2를, 목적 기준으로 묶으면 표1을 그릴 수 없습니다.

| 3 | **같은 업체가 위탁·제휴 양쪽에 등재** | 우리은행(위탁 3 + 제휴 1), 우리카드(위탁 1 + 제휴 1). 한 회사가 두 법적 지위를 동시에 가지므로 구분 표기가 필요합니다 |
| 4 | **"위탁계약을 체결한 투자권유대행인"이 제휴 표에** | 명칭에 *"위탁계약"* 이 들어 있는데 제휴 표에 있습니다. **위탁인지 제휴인지 명칭 자체가 어긋납니다** **[확인 필요]** |
| 5 | **집합적 지칭** | 위 항목은 특정 상호가 아니라 *"…와 위탁계약을 체결한 투자권유대행인"* 이라는 집합입니다. 수탁자·제공받는 자를 특정하도록 요구하는 취지와 맞는지 확인이 필요합니다 **[확인 필요]** |
| 6 | **컬럼 용어 불일치** | 표1 *"정보**항목**"*, 표2 *"정보의 **종류**"* |
| 7 | **오탈자·띄어쓰기** | *"포**토**폴리오"* → 포트폴리오, *"투자자문서비스**및**"*, *"PowerBase전산서비스이용계약서에의거한"* |

> **1번과 4번은 내용상의 문제**라 조치가 필요하고, 2·6·7번은 **수기 관리의 전형적 증상**입니다.
> 도구에 **정합성 점검**을 넣어 이 7가지를 자동으로 찾아내도록 했습니다.
> 제목도 어긋나 있습니다 — 팝업 제목은 *"위탁 및 제휴 현황"*, 제8조 링크 문구는 *"위탁 및 제휴**업체** 현황"* 입니다.

#### 담당부서 변경은 개정인가 — 아니오, 가장 명확한 경우입니다

**결론: 개정이 아닙니다.** 근거는 세 가지입니다.

| # | 근거 |
|---|---|
| 1 | 「개인정보 보호법」 **제26조 제2항이 공개하도록 요구하는 것은 "위탁하는 업무의 내용"과 "수탁자"** 입니다. 담당부서는 법정 공개 항목이 아니라 **당사가 자발적으로 추가한 관리 정보**입니다 **[확인 필요 — 시행령 확인]** |
| 2 | **정보주체의 권리·의무에 영향이 없습니다.** 위탁받는 자·업무·항목이 그대로면 처리의 실질이 동일합니다 |
| 3 | 제14조(개인정보 보호책임자 및 담당부서)의 부서와는 **성격이 다릅니다.** 그것은 제30조 제1항 **법정 기재사항**이자 정보주체의 **문의·권리행사 창구**라 실질적 의미가 있습니다 |

**다만 두 경우를 구분해야 합니다.**

| 경우 | 성격 | 처리 |
|---|---|---|
| **부서명 자체가 변경** (IT기획부 → IT본부) | 명칭만 바뀌고 담당 실체는 동일 | **일괄 치환.** 사유 1건이 변경 N건을 묶는 **ChangeSet** — 신구대조표의 비고 셀 병합과 같은 구조 |
| **담당 부서가 이관** (CX기획부 → 리테일성장실) | 관리 주체가 실제로 바뀜 | 개별 변경. **인수인계 관점에서 기록이 중요** |

둘 다 개정은 아니지만 **기록의 성격이 다릅니다.** 앞은 조직 마스터 한 줄 수정으로 끝나야 하고,
뒤는 누가 언제 넘겨받았는지가 남아야 합니다.

**그리고 실무적으로 여기가 가장 아픕니다.**

| 부서 | 등재 건수 |
|---|---|
| IT기획부 | **10건** |
| 리테일성장실 | 9건 |
| CX기획부 · 자금부 · 디지털PB센터 | 각 4건 |
| 영업솔루션부 · 종합금융사업추진부 | 각 1건 |

*"IT기획부 → IT본부"* 한 번이면 **워드에서 10곳을 고쳐야 합니다.**
방침 본문·신용정보활용체제까지 합치면 더 늘어나고, **누락이 구조적으로 발생**합니다.
조직 마스터 연동과 **일괄 치환**이 필요한 이유입니다.

> 주의 — **담당부서와 위탁 내용이 함께 바뀌는 경우**는 본문 검토 대상입니다.
> 도구는 *"담당부서만 바뀐 변경"* 을 따로 식별해 이 경우를 구분합니다.

#### 본문 표와 팝업 표의 기재 수준이 다르다

제8조 본문 표의 **제공 항목**은 범주 서술입니다 — *"가. 개인식별정보 / 나. 금융(거래)정보"*.
반면 팝업 표는 구체 항목입니다 — *"주민등록번호", "핸드폰번호", "소개관리번호, 진행상태, 취급일, 취급금액"*.

두 곳이 **서로 다른 파일에서 따로 관리**되면 한쪽만 갱신되는 불일치가 구조적으로 발생합니다.
단일 출처에서 두 뷰(요약/상세)를 생성하는 방식이 필요합니다.

#### 결정적 근거 — 당사 방침이 이미 스스로 약속하고 있다

제8조 표 아래에 다음 문장이 있습니다.

> *"위탁계약 시 개인(신용)정보보호 관련 법규의 준수, 개인(신용)정보에 관한 제3자 제공 금지 및 책임 부담 등을
> 명확히 규정하고, 당해 계약 내용을 보관하고 있습니다.* **업체 변경 시 공지사항 및 개인정보처리방침을 통해
> 고지하겠습니다.***"*

**수탁사가 바뀌면 고지하겠다고 방침 본문에 명시**되어 있습니다.
제17조의 *"변경 전·후를 비교하여 공개합니다"* 와 정확히 같은 구조입니다 —
**법령 이전에 방침상의 자기 구속이고, 이행 수단이 지금 없습니다.**

> 이 문장 하나로 "현황 이력 관리가 필요한가"라는 질문은 종결됩니다.
> 필요 여부를 따질 것이 아니라, **이미 약속한 것을 이행할 수단이 없는 상태**입니다.

#### 어느 문서가 이 현황을 참조하는가 — 문서별 적용 여부

당사가 관리하는 3개 문서 중 **2개가 같은 현황 문서를 참조**합니다.

| 문서 | 위·수탁 현황 | 근거 |
|---|---|---|
| **개인정보처리방침** | **필요** | 제8조(개인정보 처리업무의 위탁)에서 참조 |
| **신용정보활용체제** | **필요** | 제3조 라.에서 *"개인(신용)정보 관련 업무 위탁·제휴현황 — 홈페이지 > 개인정보처리방침 > '…현황' 참고"* 로 **동일 문구·동일 대상** 참조 |
| **고객정보취급방침** | **해당 없음** | 「금융지주회사법」 제48조의2에 따른 **그룹사 간 고객정보 제공·이용** 문서. 본문에 **제공처(그룹사 목록)** 가 직접 기재되며 제3자에게 처리를 맡기는 **위탁**과는 개념이 다름. 게시 원문에도 항목이 없고, **그룹 제정 문서라 당사가 추가할 수도 없음** |

> 두 문서가 같은 현황을 참조하므로, 현황은 **특정 문서의 하위가 아니라 문서 간 공유 개체**여야 합니다.
> 문서별 사본을 두면 한쪽만 갱신되는 불일치가 구조적으로 발생합니다.

#### 현황 변경이 방침 개정은 아니지만, 이력이 면제되는 것은 아니다

분리의 목적은 "수탁사가 바뀌어도 개정하지 않기 위해서"입니다. 그러나 그것이 **기록하지 않아도 된다**는 뜻은 아닙니다.

| 판단 | 근거 |
|---|---|
| 수탁사만 바뀌면 **방침 개정이 아니다** | 본문이 목록을 담지 않고 참조만 하므로, 참조 대상이 갱신될 뿐 본문 조문은 불변 |
| 그러나 **공개 의무는 그대로 남는다** | 「개인정보 보호법」 **제26조 제2항**의 위탁 업무 내용·수탁자 공개 의무는 **제30조(처리방침)와 별개**로 존재. 개정 절차를 밟지 않을 뿐 **지체 없이 갱신**해야 함 |
| 무엇보다 **당사 방침이 스스로 고지를 약속**했다 | 제8조 말미 *"업체 변경 시 공지사항 및 개인정보처리방침을 통해 고지하겠습니다"* — 법령 이전에 **방침상의 자기 구속** |
| **담당부서 변경(조직개편)도 현황을 바꾼다** | 팝업 표가 담당부서를 공개하므로 조직개편 시 갱신 필요. 위탁 내용은 불변이므로 **본문 검토 대상은 아님** |
| 그래서 **현황 자체의 버전·스냅샷이 필요하다** | 방침 이전본에는 수탁사 목록이 없음(별도 문서이므로). 현황의 시점별 스냅샷이 없으면 **"2025년 6월에 어느 수탁사에 위탁하고 있었는가"를 입증할 수 없음** |

> **보완 결론:** Registry는 방침과 **분리**될 뿐 아니라, 자체 **버전축(g1…gN)과 스냅샷**을 가져야 합니다.
> 기준일 하나만으로는 "지금 기준"만 알 수 있고 "그때 기준"은 복원할 수 없습니다.
> 상세 설계는 `02-관리체계-개선-기획안.md` 2-5절 및 원칙 P6 참조.

### 9-7. 변경내역 공개 방식 — 3사 정면 비교

방침 본문만큼 중요한 것이 **"이번에 무엇이 바뀌었는가"를 정보주체에게 어떻게 전달하는가**입니다.
개인정보 보호법 시행령상 변경 시 변경 내용을 지속 공개하고 정보주체가 쉽게 알 수 있도록 해야 하며,
당사 제17조는 이를 **"변경 전·후를 비교하여 공개합니다"라고 명문화**하고 있습니다.

| 비교축 | 토스증권 | 카카오페이증권 | **우리투자증권** |
|---|---|---|---|
| 변경내역 제공 위치 | 제18조 말미 `>> 개인정보 처리방침 과거 변경 내역` | 제15조 말미 `[개인정보 처리방침 개정내역 조회]` | 제17조 말미 `개인정보처리방침 개정내역` |
| 버전별 변경내용 링크 | 통합 문서 1개 | **버전마다 `[개정내용]` 개별 링크** (V.1~V.14) | 통합 링크 1개 |
| 신구대조표 | **웹 3열 표** (변경 전/변경 후/비고) | **PDF 첨부** (`신구대조표_20260529.pdf`) | 별도 신구비교표 (**수기 작성**) |
| 대조 형식 | **좌우 병렬** | 미확인 (PDF 내부) | 미확인 |
| 변경 부분 표시 | **셀 내부 부분 하이라이트** | 미확인 | 미확인 |
| 신설·삭제 표기 | **한쪽 셀을 비움** | 미확인 | 미확인 |
| 변경 사유 기재 | **100% 기재** (비고 셀 병합으로 공란 없음) | 미확인 | 미확인 |
| 생성 방식 | 미확인 (형식상 자동 생성 추정) | 수기 작성 → PDF 첨부 | **수기 작성** |
| 이전본 열람 | 32개 버전 날짜 선택 | 14개 버전 개별 링크 | **7개 버전 + 적용기간 명시** |

세 곳 모두 변경내역을 제공하고는 있으나, **제공 형태의 결이 다릅니다.**

- **카카오페이증권이 가장 충실합니다.** 버전마다 `[개정내용]`을 따로 걸어두어,
  정보주체가 **"내가 관심 있는 그 시점의 변경만"** 골라 볼 수 있습니다. 신구대조표 PDF도 최신본에 첨부합니다.
- **토스증권**은 변경 내역을 **별도 문서로 분리**해 상시 제공합니다. 본문(제18조)에서 링크로 연결됩니다.
- **당사**는 개정내역 링크와 이전 방침 링크를 제공하나, **신구비교표를 사람이 직접 작성**합니다.

#### 토스증권 신구대조표에서 확인된 형식 (캡처 기준)

토스증권의 「개인정보 처리방침 변경내역」 화면을 확보하여 형식을 확인했습니다.
**본문 텍스트는 캡처 해상도상 판독 불가**하나, 표 구조·열 구성·강조 방식은 명확히 식별됩니다.

| # | 확인된 형식 | 시사점 |
|---|---|---|
| 1 | **PDF가 아니라 웹 페이지**로 제공 | 검색·링크·모바일 대응 가능. 조항 데이터에서 직접 렌더링 가능한 구조 |
| 2 | **3열 표 — 변경 전 / 변경 후 / 비고** | 국내 신구조문대비표 관행(법제처 형식)과 동일한 **좌우 병렬** |
| 3 | 행 단위 = **조항 또는 문단 단위** | 문서 통째 비교가 아니라 단위 비교. 조항 단위 저장의 산출물 |
| 4 | **셀 내부 부분 하이라이트** | 문장 전체가 아니라 **바뀐 조각만** 색으로 강조. 단어 단위 Diff |
| 5 | **신설·삭제는 한쪽 셀을 비움** | 신설 = 변경 전 공란 / 삭제 = 변경 후 공란 |
| 6 | 강조 방식은 **볼드 + 밑줄** | 색상에만 의존하지 않음. 색각 이상·흑백 출력에서도 식별 가능 |
| 7 | **비고 셀을 rowspan으로 병합** | 하나의 사유가 여러 변경을 묶음. **공란이 발생하지 않음** |
| 8 | 긴 조항의 미변경 구간은 **`(중략)`으로 생략** | 전문을 다 싣지 않고 변경 지점 주변만 노출 |
| 9 | 스크롤 수십 화면 분량의 **전문 대조표** | 요약 계층 없음. 아래 참조 |

> **[확인 필요]** 변경내역이 개정 건별로 분리 제공되는지(카카오페이증권 방식)는 캡처만으로 단정할 수 없습니다.
> 화면 상단에 선택기로 보이는 요소가 있어 개정 건별 조회가 가능할 것으로 추정되나, 실물 확인이 필요합니다.

#### 핵심 발견 — 사유는 "변경 1건"이 아니라 "변경 그룹"에 붙는다

토스증권 신구대조표에서 가장 배울 점입니다. 실제 사례:

```
비고: "안전성 확보조치 대상에 개인정보 및 개인신용정보가 모두 포함되어,
      조문 전반의 '개인정보'를 '개인(신용)정보'로 용어 명확화"
      ↑ 이 사유 하나가 아래 여러 변경을 한꺼번에 설명하며, 셀이 병합되어 있음

  ├─ 1. 개인정보의 암호화              → 개인(신용)정보의 암호화
  ├─ 2. 해킹 등에 대비한 기술적 대책     → (동일 용어 치환)
  ├─ 3. 개인정보 처리 시스템 접근 제한   → 개인(신용)정보 처리 시스템 접근 제한
  └─ 4. 개인정보 취급 직원의 최소화·교육  → 개인(신용)정보 취급 직원의 최소화·교육
```

용어 하나를 조문 전반에서 일괄 치환하면 변경 지점이 수십 곳 생깁니다.
여기에 **사유를 지점마다 반복 기재하면 읽을 수 없는 표**가 됩니다.
토스증권은 이를 **하나의 사유 + 병합 셀**로 묶어 해결했습니다.

> **데이터 모델 영향**: 사유(`reason`)를 개별 변경(`Change`)의 속성으로 두면 이 구조를 만들 수 없습니다.
> **`ChangeSet`(변경 그룹) 계층을 별도로 두고, 그 아래에 개별 변경을 매다는** 구조여야 합니다.
> 이는 업무 실제와도 맞습니다 — 담당자는 "이번에 왜 고치는가"를 **건별이 아니라 사안별로** 정의하기 때문입니다.

#### 토스증권에서 배울 것 vs 당사가 앞설 수 있는 것

**배울 것 — 변경 사유 기재 수준**

토스증권은 **모든 변경에 사유를 기재**합니다. 개정일자 한 줄만 바뀌어도 비고에 "개정일자 반영"이라고 씁니다.
당사는 사유가 데이터로 남지 않으므로, **이 항목은 따라가야 할 대상**입니다.
다만 사유를 지점마다 반복하지 않고 **그룹 단위로 묶어 병합**하는 방식까지 함께 가져와야 실제로 읽히는 표가 됩니다.

**앞설 수 있는 것 — 요약 계층**

토스증권의 변경내역은 처음부터 끝까지 **전문 대조표**입니다. 스크롤 수십 화면 분량이라
정보주체가 "이번 개정에서 나에게 영향 있는 항목"을 파악하려면 전체를 훑어야 합니다.
**선두 업체조차 "직관적 확인"은 달성하지 못한 상태**입니다.

→ **정보구조를 3계층으로 두면 당사가 앞설 수 있습니다.**

```
1계층  변경 요약        이번 개정에서 무엇이 바뀌었는지 한 문장 + 신설/수정/삭제 건수
2계층  변경 그룹 카드    사유별로 묶인 변경 목록 (사유 · 영향 조항 · 유형)
3계층  전문 신구대조표   좌우 병렬 3열 + 비고 셀 병합 + (중략) 생략  ← 토스증권은 여기부터 시작
```

이 3계층은 **`ChangeSet` 모델이 있어야 성립**합니다. 1·2계층이 곧 `ChangeSet` 단위의 뷰이기 때문입니다.

#### 수기 작성이 만드는 두 가지 문제

**① 누락이 구조적으로 가능합니다.**
수기 비교표는 "바뀐 것을 기억해서 적는" 방식입니다. 당사 방침은 17개조에 대형 표가 다수 포함되어 있어
표 안의 한 행이 바뀐 경우 특히 누락되기 쉽고, **누락 여부를 검증할 수단도 없습니다.**
조항 단위로 저장되어 있으면 비교표는 **계산 결과**이므로 누락이 원리적으로 발생하지 않습니다.

**② 정보주체가 직관적으로 확인하기 어렵습니다.**
별도 문서를 열어 전체를 훑어야 하고, "이번 개정에서 나에게 영향 있는 항목이 무엇인지"가 한눈에 들어오지 않습니다.
이는 2024년 시행된 **개인정보 처리방침 평가제**(법 제30조의2)의 가독성·접근성 관점에서도 불리합니다.

> **핵심**: 당사는 **선언은 되어 있고 이행 수단이 수작업**인 상태입니다.
> 제17조가 이미 "변경 전·후를 비교하여 공개"를 약속하고 있으므로,
> 이 과제는 **새 의무를 만드는 것이 아니라 이미 선언한 의무를 시스템으로 이행하는 것**입니다.
> 사내 설득에서 가장 방어하기 쉬운 논거입니다.

#### 설계상 반드시 구분할 것 — 감사 로그와 공개 변경내역은 다르다

같은 `ChangeLog` 데이터에서 나오지만, **노출 범위가 다릅니다.**

| | 내부 감사 로그 | 대고객 변경내역 |
|---|---|---|
| 목적 | 통제·증빙 | 정보주체 고지 |
| 포함 | 변경자, 검토자, **승인자**, 결재 일시, 초안 이력, 스냅샷 해시 | 시행일, 변경 조항, 변경 유형, **변경 사유**, 변경 전·후 |
| 제외 | — | **담당자 실명·결재 정보는 노출하지 않음** |
| 열람 권한 | 내부 권한자 | 누구나 |

> 하나의 변경 기록에서 **두 개의 뷰를 생성**하되, 대고객 뷰에는 내부 결재 정보가 새어 나가지 않도록
> 필드 단위로 공개 여부를 지정해야 합니다. 이 구분을 설계 초기에 하지 않으면
> 나중에 "감사 로그를 그대로 공개"하거나 "공개용을 또 수기로 만드는" 두 가지 잘못된 선택지만 남습니다.

### 9-8. 벤치마킹할 구체 사례 — 카카오페이증권의 HTML/PDF 병행

카카오페이증권 페이지 하단 링크 구성입니다.

```
이용약관 │ 보호금융상품등록부 │ 개인정보처리방침 │ 개인정보처리방침 PDF │
고객권리안내문 │ 신용정보 활용체제 │ 신용정보 활용체제 PDF │ 주문 장애시 대처방법
```

**HTML 본문과 PDF를 나란히 제공**하고 있습니다. 5-2에서 제안한 `/privacy-policy` + `/privacy-policy.pdf` 구조와 정확히 일치합니다.
또한 각 과거 버전마다 **`[개정내용]` 링크**를 붙이고, 최신본에는 **`개인정보 처리방침 신구대조표_20260529.pdf`** 를 첨부했습니다.

> 즉 **"HTML이 원본, PDF는 산출물"** 구조는 이미 동종 업계에서 운영 중인 검증된 방식입니다.
> 사내 보고 시 "새로운 시도"가 아니라 **"업계 표준 따라잡기"** 로 포지셔닝할 수 있습니다.
